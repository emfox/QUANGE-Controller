# 原厂固件静态分析

> 2026-11-08，基于自有设备导出的 `firmware/rom_512k.bin` 及切片 `firmware/rom_vendor_firmware.bin`。
> 纯静态分析，未运行、未修改固件。复现：`python tools/rom_analyze.py`（加 `--logs` 打印全部 200 条日志槽），只依赖 Python 标准库。

## 1. 镜像结构

全片 524,288 B，其中 82.0% 是 `0xFF`。非空白区域（`tools/rom_analyze.py` 自动列出）：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| `0x00000–0x0D3E4` | 54,244 B | **原厂固件**（代码 + 常量 + 广播/GATT 数据） |
| `0x20000–0x29AE4` | 39,652 B | 导出时刷入的 `BLE-Hacker.bin`，非原厂内容 |
| `0x40000–0x40641` | 1,601 B | **运行日志表**，200 槽 × 8 B（见 §4） |
| `0x41000`、`0x42000`、`0x45000`、`0x46000` | 若干 | 配置标量（见 §4） |
| `0x76000–0x76008` | 8 B | MAC + 2 B 校准 |
| `0x77000` / `0x770C0` / `0x771C0` | 各 1–2 B | 射频校准值 |
| `0x03000–0x03FFF` | 4 KiB | 近全零数据区（仅 220 个非零字节），用途未解 |

**固件头**（`0x00–0x27`，两个镜像交叉验证）：

| 偏移 | 原厂 | BLE-Hacker | 含义 |
| --- | --- | --- | --- |
| `0x00` | `00008056` | `00008026` | RAM 相关地址 |
| `0x04` | `025d0000` | 同 | 固定配置字 |
| `0x08` | `00000000` | `544c4e4b` (`KNLT`) | pvvx 固件的 OTA 标记，原厂没有 |
| `0x0C` | `008803e9` | `008803ab` | 用途未解 |
| `0x10` | `000080c6` | `00008086` | RAM 相关地址 |
| `0x18` | **`0000d3e4` (54,244)** | **`00009ae4` (39,652)** | **固件长度**，与实测非空白区长度完全一致 |
| `0x20` | 启动代码 | 启动代码 | 两者仅差 1 字节 |
| `0x28–0xA7` | `c0 06` × 64 | 同 | 中断向量/填充槽 |

固件尾部 4 字节是校验字段。BLE-Hacker 用标准 CRC32 补码（`crc32(整块) = 0xFFFFFFFF`）；原厂用私有算法，`crc32(body[:-4]) = 0x4999d8e6` 与尾部 `0xc79156b0` 不符，尚未破解。

## 2. 代码与反汇编的可行性

芯片是 Telink **TC32** 内核，ARM9 Thumb（16 位）指令集的克隆，但 Telink 改动了 opcode 编码。用标准 Thumb 解码器（Capstone 5）实测：代码区解出的指令分布与**纯数据区**几乎一样（`lsls`/`adr`/`ldr` 占绝大多数，几乎没有 `bl`/`push`/`pop`），说明**标准 Thumb 解码器不可用**；按半字交换字节序或换大端模式也无改善。

> **2026-11-08 后续已解决**：用 [trust1995/Ghidra_TELink_TC32](https://github.com/trust1995/Ghidra_TELink_TC32)
> 仓库里从官方 objdump 提取的 opcode 表写了纯 Python 解码器 `tools/tc32_disasm.py`
> （覆盖率 99.80%），已完成全片反汇编，见 [固件功能结构](firmware-structure.zh-CN.md)。
> 本文下面的结论仍只来自头部、常量表、字符串和运行时数据区，不依赖反汇编。

## 3. 广播与 GATT：`kHID` / `0x1812` 定案

固件里两套广播数据是紧邻存放的：

- **ADV @`0xCCEC`**：`10 09` + `QUANGE-WY020702`（只有名字，后面 3 B padding）
- **SCAN RSP @`0xCD00`**：`05 09 kHID`、`02 01 05`（Flags）、`03 19 80 01`（Appearance）、`05 02 12 18 0f 18`（UUID 列表 `0x1812` + `0x180F`）、`07 ff aa×6`（Manufacturer Data 占位）

由此三件事可以确定：

1. **`kHID` 是 scan response 里的名字**，主广播包里是 `QUANGE-WY020702`。扫描器偶尔把 scan response 的名字当主名回吐，正是「每轮扫描第一个包才出现 `kHID`」的成因。
2. **全片搜索 `12 18`（`0x1812` 小端）只有 1 处命中，就在 SCAN RSP 的 UUID 列表里**；HID 的 5 个特征 UUID（`0x2A4A`/`0x2A4B`/`0x2A4C`/`0x2A4D`/`0x2A4E`）在整片 512 KiB 中**命中数全为 0**。GATT 属性表数据区（`0xCD1C–0xD090`，24 B/项，含 `0x180F`、`0x180A`、`0x2A19`、`0x2A50`、`0x2902`、`OTA`、`1001/1002` 等常量）没有任何 HID 服务/特征。广播声明 ≠ 能力，与真机 GATT 全量导出（6 个服务、无 HID）一致。
3. `Telink Remote` @`0x3A46`、`tModule` @`0x3748` 在**两个镜像的对应偏移都出现**，是 Telink HID Remote 示例 SDK 的库常量，不是应用实现的 HID 功能。加上 SCAN RSP 里那个 `kHID`，支持「上游示例配置 / 烧录时误写」的判断。

Manufacturer Data 的 6 个 `AA` 是运行时占位；`0x76000` 存的是反序 MAC `b6 9b 00 c2 45 1c`（即 `1C:45:C2:00:9B:B6`）+ `5a 90`。

其它可见字符串：`Hi-YM01-12DC2110000` @`0x2F8C`、`Hi-YM01-12DC2000000` @`0xD3BA`（GAP 默认名）、`LFWY020702/` @`0xD098`。

## 4. Flash 里的日志表（本次最重要的发现）

`0x40000` 起是 **200 槽 × 8 B** 的持久化运行记录，`0x40640` 一个字节 `01` 结束：

| 字节 | 格式 | 含义 |
| --- | --- | --- |
| `0..3` | **大端** u32 | Unix 秒（与 BLE 回包字节序一致） |
| `4..5` | **大端** u16 | 时长（秒），实测值只有 180 / 300 |
| `6` | u8 | 触发类型：`0` 定时 / `1` 手动、上电自动消杀 |
| `7` | u8 | `0xFF`（已写槽），空槽全 `0x00` |

导出时 189 个槽有数据，189–199 为空。关键对照：

- **槽 188** = `6a d9 f7 9a 00 b4 01 ff`，与真机回包 `BD0805 6AD9F79A 00B4 01 01` 的**前 7 字节逐字节一致**。日志数据确实直接来自这块 flash。
- **槽 2–177** = 2026-02-20 → 2026-08-14 每天 02:00 的定时消杀。间隔统计：86,400 s（跨天）133 次、46,800 s（02:00→15:00）13 次、39,600 s（15:00→次日 02:00）11 次 —— 说明历史上定时表基本是 **02:00 与 15:00 两条**；其中 16 条时长为 300 s，对应 15:00 那条 5 分钟设置。
- **槽 0/1** = 本次上电的运行记录，槽 1 时间戳 `0x6AEFE809` = 2026-11-08 11:10:01（导出前几分钟的上电自动消杀）；`0x46000` 的小端时钟 `0x6AEFE8EE` = 11:13:50，两者相差 229 s。
- **槽 179–187** 见下一节。

> **结论：日志没有被 ACK 删除。** 这次 dump 发生在多轮 `DB 01 05` + 45 条 ACK 排空队列之后，189 条历史记录仍完整躺在 flash 里。
> 这与 [protocol §5.3](protocol.zh-CN.md) 的「待同步队列」模型**不冲突**：那是协议视角，ACK 推进的是**同步游标/标记**，不是擦除记录；「排空」= 没有未同步记录，不是没有历史。
> 用户先前「读后删除」的猜想可以排除。
>
> 仍未证实的是游标本身存在哪一格：`0x40640 = 01`、`0x42000 = 85 (0x55)`、`0x45000 = 01` 都是候选。要坐实需再 dump 一次、消费几条新日志后对比这几处。

## 5. 时间基（补上 §8.2 的「机制未查明」）

槽 179–187 用的是另一套时间基：`0x0000FD20`、`0x00024EA0`、`0x0003A020`、`0x0004F1A0`……这是从 1970-01-01 00:00 UTC 起算的秒数。其中 **type=0 的定时记录换算成 UTC+8 后全部落在每天 02:00**（64,800 s = 18:00 UTC = 02:00 CST），与正常记录里每天 02:00 的调度完全对齐；同一批里 type=1 的手动/上电记录则是任意时刻。

也就是说：**设备时钟未对时（RTC 从 0 起算）时，日志写的是「1970 起算的秒数」；对时后写 Unix 墙钟时间戳；调度只取「秒数 mod 86400」判断本地 02:00，所以对时与否都照常触发**。这解释了真机观察到的「整批都是 3600 整数倍、看着不是墙钟」。同一时刻两块区域字节序不同（日志表大端、`0x46000` 运行时变量小端），是因为日志按 BLE 回包格式原样落盘。
