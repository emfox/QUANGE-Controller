# 原厂固件代码结构图（函数级）

对 `firmware/rom_vendor_firmware.bin`（`0x00000–0x0DFFF` 切片）做的函数级逆向。
方法见 [firmware-structure.zh-CN.md](firmware-structure.zh-CN.md) §0：纯 Python 的 TC32 解码器，
覆盖率 99.80%（26,056 条指令 / 53 条未定义）。

> 没有符号表。下面所有「名字」都是**按代码行为起的描述性标签**，地址才是硬事实。

---

## 1. 一页概览

镜像 512 KB，实际有效内容 57,316 B（`0xD3E4`）。真正是代码的只有两块，中间被一个 4 KiB 空洞隔开：

```
0x00000 ┌──────────────────────────────┐
        │ 头 0x00–0x1F                 │  复位向量在 0x00 → 0xB0
0x00020 │ 中断桩 + 64 个 nop           │  0x20 写 0x80006F=0x81 后返回
0x000B0 │ 启动 / 初始化 / 基础库 / main│  main = 0x760
0x02F8C │ 代码 A 结束                  │  紧跟一段 ASCII 与零填充
0x03000 ├──────────────────────────────┤
        │ 4 KiB 近全零（无任何引用）   │
0x04000 ├──────────────────────────────┤
        │ 应用层 / BLE 回调 / BLE 栈   │
0x0CCD6 │ 代码 B 结束                  │
0x0CCE0 │ 广播名、GATT 属性表、字符串  │
0x0D104 │ 事件回调表（83 项）          │
0x0D31C │ 指针表（30 项）              │
0x0D3E4 └──────────────────────────────┘
```

> ⚠️ 上一版布局表把 `0x028–0x0A7` 当成「64 项向量表」，**是错的**：那 64 个半字
> 解出来就是 `tmov r8, r8`（`0x06C0`），是**对齐用的 nop 填充**，不是跳转表。

## 2. 启动链

| 地址 | 动作 |
| --- | --- |
| `0x000` | `tj.n 0xB0` —— 复位向量，只有这一条指令 |
| `0x002–0x01F` | 头部字段：`0x18` = 固件长度 `0xD3E4`；`0x10` 另有一个 `tj.n 0x1A0` |
| `0x020` | **中断桩**：`tpush {r2,r3}` → `r2=0x81` → 写 `0x80006F` → nop 填充 → `0xA8 tpop {r2,r3}; tjex lr` |
| `0x0B0` | 读 flash 地址 `0x04`，等于 `0xA5` 就把 `0x05` 搬到 `0x80063E`（保留唤醒标记） |
| `0x0C2` | flash 唤醒：`0x80000C=0xAB`、延时、`0x80000D=1` |
| `0x0DA` | 把 `0x844900–0x84491F` 填 `0xFFFFFFFF` |
| `0x0EA` | `tmcsr 0x12` → `sp=0x844AC0`；`tmcsr 0x13` → `sp=0x848000`（切模式/双栈） |
| `0x0FA` | 清 `0x844940–0x844BD8`、`0x844000–0x8440FF` |
| `0x118` | `0x80060C = 0x40` 然后 `0x41` |
| `0x122` | 把 `0xD3A4` 起的数据搬到 `0x844900` |
| `0x136` | `tjl 0x760` —— **调用 main** |
| `0x13A` | `tj 0x13A` —— main 返回后死循环 |

**main = `0x760`**，开头就是四个回调指针入 RAM（存的都是 `+1` 的地址，TC32 的指针约定）：

```
0x0ED0 → 0x844BCC      0x1378 → 0x844BC8
0x7520 → 0x844B14      0x13E8 → 0x844B10
0x8435D8[1] = 1
→ 0x0D64() → 0x14B8(2) → 0x0B18() → 0x08C0(0x42)
→ analog(0x8A) 读-改-写 bit6
```

`0x8C0` 是「引脚配置」：把引脚号写 `0x800066`、存 `0x8435C8`，引脚 32 走 analog 特例，
最后 `0x800620 = 0x80B600`（输出使能位图）。

## 3. 区域表（按调用指纹划分）

「调用 →」列是该区段 `tjl` 目标的高位分布（每格 `0x800` 宽），「IO」是 literal 引用最多的寄存器。

| 范围 | 指令数 | 角色 | 证据 |
| --- | --- | --- | --- |
| `0x000B0–0x02F8C` | 5,778 | 启动、初始化、基础库、main | 调 `0x800` 段 107 次（HAL）；IO `0x800740`×33、`0x80000C/D`×32、`0x800643`×18、`0x800F20`×11 |
| `0x04000–0x04FFF` | 1,928 | **应用控制逻辑**（消杀状态机、软定时回调） | 大量引用 `0x842F34`（3 项软定时器数组）；IO `0x80059B`、`0x800580`、`0x800780` |
| `0x05000–0x058FF` | 1,111 | **协议命令分派**（见 protocol §3.6） | 唯一引用 `0x844ACC` 回包缓冲 |
| `0x05900–0x065FF` | 1,584 | **存储层**：日志表、队列索引、状态持久化 | 引用 `0x40000/0x42000/0x45000/0x46000` |
| `0x06600–0x071FF` | 1,455 | **外设驱动**（GPIO 密集） | 调 `0x800` 段 **77 次**；IO `0x800540/0x800548/0x800581/0x800586` |
| `0x07200–0x077FF` | 713 | 基础库：`memcpy/memset/memcmp`、字符串、等待循环 | `0x719C`/`0x7200`/`0x7214` 入口在这里 |
| `0x07800–0x087FF` | 1,992 | **BLE 事件 / GATT 回调层** | `0xD104` 的 83 项**全部**落在这两段（11 个不同入口） |
| `0x08800–0x09FFF` | 2,980 | BLE 射频 / 基带 | IO `0x800F00/0x800F20/0x800C2A/0x800C2B` |
| `0x0A000–0x0AFFF` | 1,984 | BLE 协议栈（链路层以上） | IO `0x800F01/0x800F03`；RAM `0x8439xx/0x843Bxx` |
| `0x0B000–0x0B7FF` | 993 | 协议栈 ↔ 应用粘合 | 回调 `0x800` 段 12 次；RAM `0x843Cxx/0x843Dxx` |
| `0x0B800–0x0BFFF` | 968 | **指针表 `0xD31C` 的 23 个目标全在这里** | `0x800740`×13，几乎每个函数都读 tick |
| `0x0C000–0x0CFFF` | 1,579 | GPIO / 模拟前端驱动 | IO `0x800540/0x800548/0x800550/0x800560` |

调用关系上，`0x8800–0x0CFFF` 是一个**自洽的大簇**（互相调用远多于对外），符合「链接进来的 BLE 库」；
`0x7800–0x087FF` 只调库、不被人调（除事件表），符合「应用侧回调」。

## 4. 已确认的基础函数

| 地址 | 作用 | 判据 |
| --- | --- | --- |
| `0x0840` | `analog_read(addr)` | 写 `0x8000B8`、置 `0x8000BA` bit6、轮询、读 `0x8000B9`；被 77 个函数调用 |
| `0x0880` | `analog_write(addr,val)` | 同上但写 `0x8000B9` |
| `0x08C0` | `gpio_set_func(pin)` | 写 `0x800066`、`0x8435C8`、`0x800620` |
| `0x0934` | `flash_cmd(cmd)` | `0x80000D=1` → `0xBF8(1)` → `0x80000C=cmd` → 等 bit16 |
| `0x08F4` | `flash_send_addr(a)` | 24 位地址分三字节推入 `0x80000C`，每次等 `0x80000D` bit4 |
| `0x09A4` | `flash_erase_sector(addr)` | `flash_cmd(8)` + `flash_send_addr` |
| `0x09E4` | `flash_write(addr,len,buf)` | 逐字节写 `0x80000C` |
| `0x0A40` | `flash_read(addr,len,buf)` | 同上，方向相反 |
| `0x09ACC` | 运行时长/状态门（返回 `0xFFFF` 表示状态字节 ≠ 8） | 被擦写路径拿来卡「上电 300 s 内不写 flash」 |
| `0x719C` / `0x7200` / `0x7214` | `memcmp` / `memset` / `memcpy` | 逐字节比较/填充/拷贝，参数 `(dst,val,len)` |
| `0x41B4` | `timer_add(id, interval)` | 写数组 `0x842F34`（3 项 × 12 B），`[+0]=id`、`[+4]=deadline`、`[+8]=interval` |
| `0x4308` | `timer_cancel(id)` | 在 `0x842F34` 里线性查找 id 并删除 |
| `0x0506E` | 协议命令分派 | 见 protocol §3.6 |
| `0x0590C` | 状态落盘 | 写 `0x42000`/`0x46000` |
| `0x05994` | 日志追加 | 读-改-写整个 `0x40000` 扇区，索引在 `0x45000` |
| `0x05AFC` | 日志取当前条 | 读 `0x45000`，`0xFF` 返回 NULL |
| `0x05BA4` | 日志确认 | `0x45000` 减一（`0` 变 `0xFF`） |

## 5. 应用层链路

```
BLE 事件  ──►  0xD104 事件表（83 项，70 项指向同一个默认处理 0x7AF2）
              └► 0x07800–0x087FF 的 11 个回调
                    └► 0x0506E 命令分派（按 frame[2]）
                          ├► 0x05900–0x065FF 存储层：日志 / 定时表 / 状态
                          └► 0x04000–0x04FFF 控制逻辑：消杀启动/停止、时长计时
                                └► 0x041B4 / 0x04308 软定时器（数组 0x842F34）
```

一次消杀的时间线对应代码：

1. 定时器到点或收到 `DB 02 04 01` → 控制逻辑置状态、开 GPIO；
2. 本次开始时间写 `0x84355C+0x3C`、时长写 `+0x48` 之类（见 structure §3.2 的 RAM 表）；
3. 到点结束 → `0x64D0` 取差值 → `0x5F4C` 组装 8 字节记录 → `0x5994` 追加进 flash；
4. 状态帧（`DB 04 02`）读的就是这块 RAM。

## 6. 两张指针表

| 表 | 位置 | 项数 | 指向 |
| --- | --- | --- | --- |
| 事件回调表 | `0xD104` | 83（11 个不同） | 全部在 `0x7800–0x7FFF`，默认 `0x7AF2` |
| 指针表 | `0xD31C` | 30（23 个不同） | 全部在 `0x0B882–0x0BF52`，间隔 30–160 B |

`0xD31C` 那 30 个目标全都读 tick（`0x800740`），且集中在 `0xB800` 段——更像「带超时的状态机表」
而不是普通函数指针数组。**具体谁遍历这张表还没找到**（没有 literal 指向 `0xD31C`）。


## 8. 还不知道的

- `0x1A0` 那个第二入口（头部 `0x10` 指向它）是什么。
- `0xD31C` 表的遍历者；`0x1DC` 的本体（像硬件通道，但结果是 `÷60`）。
- `0x0ED0` / `0x1378` / `0x7520` / `0x13E8` 四个回调分别处理什么事件。
- `0x042F34` 软定时器里 `0x6309` / `0x6539` 两个 id 的语义。
- `0x3000` 4 KiB 空洞的用途（不是代码，也没有任何引用）。
- 消杀/UV 具体是哪几个引脚（`0x800540/0x800548` 段有 20+ 处读写，未逐点对应）。
