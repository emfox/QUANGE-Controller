# 原厂固件代码结构图（函数级）

对 `firmware/rom_vendor_firmware.bin`（`0x00000–0x0DFFF` 切片）做的函数级逆向。
方法见 [firmware-structure.zh-CN.md](firmware-structure.zh-CN.md) §0：纯 Python 的 TC32 解码器，
覆盖率 99.80%（26,056 条指令 / 53 条未定义）。

> 没有符号表。下面所有「名字」都是**按代码行为起的描述性标签**，地址才是硬事实。

---

## 1. 一页概览

镜像 512 KB，实际有效内容 57,316 B（`0xD3E4`）。真正是代码的只有两块，中间被一个 4 KiB 空洞隔开：

```
0x00000 ┌──────────────────────────────┐
        │ 头 0x00–0x1F                 │  复位向量在 0x00 → 0xB0
0x00020 │ 中断桩 + 64 个 nop           │  0x20 写 0x80006F=0x81 后返回
0x000B0 │ 启动 / 初始化 / 基础库 / main│  main = 0x760
0x02F8C │ 代码 A 结束                  │  紧跟一段 ASCII 与零填充
0x03000 ├──────────────────────────────┤
        │ 4 KiB 近全零（无任何引用）   │
0x04000 ├──────────────────────────────┤
        │ 应用层 / BLE 回调 / BLE 栈   │
0x0CCD6 │ 代码 B 结束                  │
0x0CCE0 │ 广播名、GATT 属性表、字符串  │
0x0D104 │ switch 跳转表（83 槽 / 13 个 case）│
0x0D31C │ 指针表（30 项）              │
0x0D3E4 └──────────────────────────────┘
```

> ⚠️ 上一版布局表把 `0x028–0x0A7` 当成「64 项向量表」，**是错的**：那 64 个半字
> 解出来就是 `tmov r8, r8`（`0x06C0`），是**对齐用的 nop 填充**，不是跳转表。

## 2. 启动链

| 地址 | 动作 |
| --- | --- |
| `0x000` | `tj.n 0xB0` —— 复位向量，只有这一条指令 |
| `0x002–0x01F` | 头部字段：`0x18` = 固件长度 `0xD3E4`；`0x10` 另有一个 `tj.n 0x1A0` |
| `0x020` | **中断桩**：`tpush {r2,r3}` → `r2=0x81` → 写 `0x80006F` → nop 填充 → `0xA8 tpop {r2,r3}; tjex lr` |
| `0x0B0` | 读 flash 地址 `0x04`，等于 `0xA5` 就把 `0x05` 搬到 `0x80063E`（保留唤醒标记） |
| `0x0C2` | flash 唤醒：`0x80000C=0xAB`、延时、`0x80000D=1` |
| `0x0DA` | 把 `0x844900–0x84491F` 填 `0xFFFFFFFF` |
| `0x0EA` | `tmcsr 0x12` → `sp=0x844AC0`；`tmcsr 0x13` → `sp=0x848000`（切模式/双栈） |
| `0x0FA` | 清 `0x844940–0x844BD8`、`0x844000–0x8440FF` |
| `0x118` | `0x80060C = 0x40` 然后 `0x41` |
| `0x122` | 把 `0xD3A4` 起的数据搬到 `0x844900` |
| `0x136` | `tjl 0x760` —— **调用 main** |
| `0x13A` | `tj 0x13A` —— main 返回后死循环 |

**main = `0x760`**，完整流程（`0x7A0` 起是循环入口）：

```
0x760  tpush {r4,r5,lr}
       [0x844BCC] = 0x0ED1   [0x844BC8] = 0x1379     ; 存的是 +1 的 Thumb 指针
       [0x844B14] = 0x7521   [0x844B10] = 0x13E9
       [0x8435D9] = 1
       0x0D64()  → 0x14B8(2) → 0x0B18() → 0x08C0(0x42)
       读 analog 0x8A，改 bit6 写回
0x7A0  if ([0x8435D8] != 0) goto 0x7CE            ; 唤醒标记
       if ([0x842F30] != 0 && byte[[0x842F30]] != 0xFF) analog(0x8A) 读-改-写 bit0-5
0x7CE  if (r4 != 0) goto 0x7D6                    ; 保留唤醒：跳过栈初始化
0x7F8  0x4000()   ; 读 flash 0x0AB8，按 byte[+2] 是 19/20 把 0x842F2C/0x842F30 设成
                  ;   0xEC000/0xEE000 或 0xFF000/0xFE000
0x7FE  0x3EC()
0x802  0x4708()   ; BLE 栈初始化（见 §9）
0x806  0x6570()   ; 读 flash 0x42000（== 0x55 判首次）与 0x44000 → 0x8435BE
0x7D6  0x434() → [0x800643] = 1（开中断）→ 0x4478() → 0x437C() → 0x660C()
0x7F0  [0x800623] = 8 ; 0x48EC() ; goto 0x7F0     ; ← 主循环，永不返回
```

`0x8C0` 是「引脚配置」：把引脚号写 `0x800066`、存 `0x8435C8`，引脚 32 走 analog 特例，
最后 `0x800620 = 0x80B600`（输出使能位图）。

`0x8C0` 是「引脚配置」：把引脚号写 `0x800066`、存 `0x8435C8`，引脚 32 走 analog 特例，
最后 `0x800620 = 0x80B600`（输出使能位图）。

## 3. 区域表（按调用指纹划分）

「调用 →」列是该区段 `tjl` 目标的高位分布（每格 `0x800` 宽），「IO」是 literal 引用最多的寄存器。

| 范围 | 指令数 | 角色 | 证据 |
| --- | --- | --- | --- |
| `0x000B0–0x02F8C` | 5,778 | 启动、初始化、基础库、main | 调 `0x800` 段 107 次（HAL）；IO `0x800740`×33、`0x80000C/D`×32、`0x800643`×18、`0x800F20`×11 |
| `0x04000–0x04FFF` | 1,928 | **应用控制逻辑**（消杀状态机、软定时回调） | 大量引用 `0x842F34`（3 项软定时器数组）；IO `0x80059B`、`0x800580`、`0x800780` |

| `0x05900–0x065FF` | 1,584 | **存储层**：日志表、队列索引、状态持久化 | 引用 `0x40000/0x42000/0x45000/0x46000` |
| `0x06600–0x071FF` | 1,455 | **外设驱动**（GPIO 密集） | 调 `0x800` 段 **77 次**；GPIO `0x800581/0x80059B/0x800593`（`0x800540/0x800548` 见 §15.5：那是 TRNG） |
| `0x07200–0x077FF` | 713 | 基础库：`memcpy/memset/memcmp`、字符串、等待循环 | `0x719C`/`0x7200`/`0x7214` 入口在这里 |
| `0x07800–0x087FF` | 1,992 | **ATT 请求分派层**（见 §6） | `0xD104` 跳转表的 13 个 case **全部**落在这段，default 也在这一段 |
| `0x08800–0x09FFF` | 2,980 | BLE 射频 / 基带 | IO `0x800F00/0x800F20/0x800C2A/0x800C2B` |
| `0x0A000–0x0AFFF` | 1,984 | BLE 协议栈（链路层以上） | IO `0x800F01/0x800F03`；RAM `0x8439xx/0x843Bxx` |
| `0x0B000–0x0B7FF` | 993 | 协议栈 ↔ 应用粘合 | 回调 `0x800` 段 12 次；RAM `0x843Cxx/0x843Dxx` |
| `0x0B800–0x0BFFF` | 968 | **`0xB874` 事件分派器及其全部 case**（表 A，见 §15.2） | `0x800740`×13，几乎每个函数都读 tick |

## 5. 应用层链路

```
ATT 收包（0x8D04，注册在 0x8439D0）
  └► 0x7A98 分派器 ──►  0xD104 跳转表（83 槽，13 个 case，default 0x7AF2 直接返回 0）
        └► 0x07800–0x087FF / 0x08028–0x0855C 的处理块
              └► 0x05064 命令分派（按 frame[2]）
                          ├► 0x05900–0x065FF 存储层：日志 / 定时表 / 状态
                          └► 0x04000–0x04FFF 控制逻辑：消杀启动/停止、时长计时
                                └► 0x041B4 / 0x04308 软定时器（数组 0x842F34）
```

一次消杀的时间线对应代码：

1. 定时器到点或收到 `DB 02 04 01` → 控制逻辑置状态（`[0x84355C+1] = 1`）、开 GPIO；
2. 本周期时长写 `+0x3C`；之后 1 Hz 回调（`0x6308`）每秒把 `+0x48`（当前时刻）和 `+0x40`（已运行秒数）各加一；
3. 到点结束 → `0x64D0` 用 `+0x48 − +0x3C` 倒推出开始时刻 → `0x5F4C` 组装 8 字节记录 → `0x5994` 追加进 flash；
4. 状态帧（`DB 04 02`）读的就是这块 RAM（剩余秒数 = `+0x3C − +0x40`，与实测 `00B4 → 0030` 吻合）。

具体字段见 §8 的表。

## 6. 两张跳转表（不是回调注册表）

上一版把 `0xD104` / `0xD31C` 当成「函数指针/回调表」，**这是错的**。它们都是 `switch` 的**跳转表**。

`0x7A98` 就是那个分派器：

```
r7 = arg1
[0x84361E] = 10
r5 = u32[0x84379C]        ; 连接上下文指针
if (r5 == 0) return 0
[r5+4] = 2 ; [r5+8] = 4 ; [r5+9] = 0
r3 = byte[r7+10]          ; ← 选择子
if (r3 > 82) return 0     ; 越界也走 default
r1 = 0xD104[r3]
pc = r1
```

表里 70 项都指向 `0x7AF2`，而 `0x7AF2` 就是 `r6 = 0; return r6` —— 那是 `default: return 0`。
所以「70 项同一目标」不是「70 个事件共用一个默认处理」，实际**只有 13 个 case**：

| slot | 处理块 |
| --- | --- |
| 2、3 | `0x7D96` |
| 4 | `0x7CB6` |
| 6 | `0x7EA4` |
| 8 | `0x7C5E` |
| 10、12 | `0x7E74` |
| 16 | `0x7E00` |
| 18、82 | `0x7C00` |
| 22 | `0x7B7C` |
| 24 | `0x7B18` |
| 30 | `0x7AFE` |

这 13 个值逐个对上 **ATT 操作码**：2 MTU Req、3 MTU Resp、4 Find Information Req、
6 Find By Type Value Req、8 Read By Type Req、10 Read Req、12 Read Blob Req、
16 Read By Group Type Req、18 Write Req、22 Prepare Write Req、24 Execute Write Req、
30 Handle Value Confirmation、82(`0x52`) Write Command。
而且 `0x8D04`（收包处理）按 `u16[conn+8]` 分三支后，正是经 `0x8D96` 调进 `0x7A98`。

⟹ 这一层是 **ATT 请求分派器**，不是应用回调层。**标记：强推断，未证实**（数值吻合度极高，
但没有符号表；不做结论性断言）。

`0xD31C` 同样是跳转表，但**它不是一张 30 项的表，而是两张 15 项的表背靠背**（§16.2）：

```
0xB8A6  r3 = r0 << 2
        r2 = 0xD31C
        r3 = u32[r2 + r3]
        pc = r3
```

`0xB8A6` 的上一句是 `tcmp r0, #14` + `tjls`（无符号 ≤ 14），所以**索引只可能是 0..14**，
只覆盖 `0xD31C–0xD357`。紧跟其后的 `0xD358` 是被 `0xC034` 那处 literal 单独引用的**第二张表**，
同样是 0..14。两张表都以 `0xBCA6`（`return 0` 风格的空 case）兜底。

⚠️ 同时收回上一版「34 个间接入口」的说法：那批地址绝大多数是这两张 switch 表的 case 标号，
不是函数指针注册。真正被代码写进 RAM 的 Thumb 指针只有 30 来个，`--indirect` 可以列全。

## 7. 软定时器与 1 Hz 秒中断

| 组件 | 地址 | 说明 |
| --- | --- | --- |
| 定时器数组 | `0x842F34` | 4 槽 × 12 B：`{fn, deadline, interval_ticks}`，count 在 `+0x30` |
| `timer_add` | `0x41B4` | `(fn, interval_us)`；内部 **`ticks = interval << 4`** |
| `timer_cancel` | `0x4308` | `(fn)`，按指针匹配后前移压缩 |
| `timer_poll` | `0x423C` | 主循环每轮调用，`now = [0x800740]`，到期调 `fn` |
| 1 Hz 回调 | `0x6308` | `[state+0x48] += 1`、`[state+0x40] += 1`，然后取本地时间 |

`interval << 4` 说明参数是**微秒**、tick 是 16 MHz：所以 `0x0F4240`(1,000,000) 就是**1 秒**，
主循环里那个 `0x4E200`(320,000) 阈值就是 **20 ms**。两个数互相印证。

`0x6309` / `0x6539` 也**不是事件 ID**——它们是 Thumb 指针（`0x6308` / `0x6538` 加 1）。
旧版「两个软定时事件的语义」这个问题问错了前提：`0x6308` 是 1 秒定时，`0x6538` 是另一个回调。

## 8. 日志的「起始时间」是算出来的

写日志的链条（之前只知道入口和落盘位置，中间那段现在通了）：

```
周期结束 → 0x64D0
    r1 = [state+0x3C]                  ; 本周期时长
    r0 = [state+0x48] - [state+0x3C]   ; 当前秒 − 时长 = 开始时刻
  → 0x5F4C(ts, dur)  打包 8 字节：BE32(ts) BE16(dur) type 0xFF
  → 0x5994           追加（整扇区读-改-写 0x40000，索引 +1）
```

**记录里的时间戳不是存下来的，而是「当前时间 − 时长」倒推的。** 这解释了实测里
「触发在 14:17:00、记录时间戳 14:16:58」的两秒差：触发判定在整秒边界，写记录在结束时刻。

于是 `0x84355C` 状态块的这几个字段也定了：

| 偏移 | 含义 |
| --- | --- |
| `+0x3C` | **当前周期时长（秒）** —— 上一版写成「起始时间」是错的 |
| `+0x40` | 本周期已运行秒数（1 Hz 自增） |
| `+0x48` | **当前秒计数**（1 Hz 自增，即「现在」） |
| `+0x50…+0x5C` | 4 个槽位配置的时长（秒） |

## 9. BLE 栈初始化与中断向量表

`0x4708` 是栈初始化（`0x802` 调用，只在冷启动分支执行；保留唤醒会跳过）：

```
0x7670 0x840 0x880 0x4044 0x1F18 0x8F20 0x907C 0x9768 0x9A48 0xAD8C
0x8898 0x58E4 0x8938(0x8D05) 0x8950(...) 0xB5E8 0x90F8 0x9184 0x91CC
0x8FE0 0x14E0 0x8E30×5 0x8944(0x4615) 0xAD8C 0xADDC 0xAFBC 0xAFDC
0x8E30 0xB4E0 0xB184(0x58F5) 0xB190(0x595D) 0x5980
```

`0x8E30(irq, handler)` 就是中断注册：`[0x8438BC + 4 + irq*4] = handler`。六项：

| IRQ | 处理函数 |
| --- | --- |
| 3 | `0x4648` |
| 4 | `0x45EC` |
| 11 | `0x460C` |
| 13 | `0x4610` |
| 14 | `0x4618` |
| 15 | `0x03E0` |

`0x8938(0x8D05)` 把 ATT 处理函数存进 `0x8439D0`（这就是 §6 里 `0x8D04` 没有静态调用者的原因）；
`0x8950(ptr, 168, 0x843048, 36)` 把两个收发缓冲的指针与长度写进 `0x84378C` 结构
（`+0x0C/+0x14` 与 `+0x10/+0x16`）。

## 10. 按键

`0x43A0` 扫 `0x800580` 的 bit6（`r2 & 0x40`），状态放在 `0x842F68`：
`+0` 有效、`+1` 边沿、`+2` 上一值、`+3` 计数、`+4` 标志位。
短按路径 `0x4440 → 0x64D0`（结束周期 → 写日志）；
`0x4684` 是长按判定（`[+3] > 15` 触发），触发后 `0xADB8(0x50)` / `0x7484(0x40,0,1)` /
`0xADDC(0x0F)` —— 与实测的「长按重启并进入自动消杀」一致。

## 11. 主循环 `0x48EC`（81 个基本块）

全部是直接跳转，**没有一处间接跳转**，所以控制流可以完整重建（`0x48EC–0x4FDA`）。
每轮固定三段：

```
[0x844B68] += 1            ; 轮次计数
0x423C()                   ; 软定时器 poll
0x1B24()                   ; BLE 栈驱动（读 0x84393C+0x78、0x8438BC+0x77）
...状态处理...
0x43A0()                   ; 扫按键（0x800580 bit6）
```

### 11.1 三个顶层门

| 变量 | 值 | 走向 |
| --- | --- | --- |
| `[0x844B98]` | `0` | 进 `0x49A4` 分支（250 ms 节奏：`[0x800740] − [0x844B8C] > 3D0900`）；否则走常规路径 |
| `[0x84358D]` 状态 | `0` / `1` | 待机 / 运行。**全固件只比较这两个值**，没有第三态 |
| `[0x842F70]` | `1` | 进 `0x4AB0` 分支（硬件已在输出）；`0` 走 `0x49D0` |

`0x844B98` **没有找到任何写入点**（只有 `0x490C` 读），大概率由栈/中断按计算地址写，未坐实。
`0x842F70` 的写入点是按键处理 `0x4452` 和启动流程 `0x6646`。

### 11.2 20 ms 心跳

```
0x4956  r0 = [0x800740] − [0x844B80]
        if (r0 > 0x4E200) {            ; 320,000 tick = 20 ms
            [0x844B80] = [0x800740]
            [0x842F68+4] |= 1
        }
```
同一个 tick 源在 `0x49A4` 那边用 `0x3D0900`（4,000,000 tick = 250 ms）做慢速节奏。

### 11.3 关键动作块

| 块 | 作用 | 证据 |

| `0x4AFC` | **启动序列**：`0xADDC(15)`、`0xADB8(16)`、`0x7484(64,0,1)`、`[0x842F68+4] |= 8`、`0x5060(0x43,16,0)` | — |

### 11.4 状态块里的五个布尔子标志

`0x84358C` 这个子结构除了状态字节 `+1`，还有 `+2`、`+3`、`+6`、`+9`、`+0xB` 五个 0/1 布尔，
主循环逐个判它们决定分支；停机路径（`0x5F94` / `0x4B60`）会把 `+2/+3` 清零。

把每个字节的读写点全列出来（`tools/tc32_ram.py --ram 84358E` 这样查），可以一一对号：

| 字节 | 绝对地址 | 写点 | 读点 | 判定 |
| --- | --- | --- | --- | --- |
| `+2` | `0x84358E` | `0x53A0` / `0x5570` / `0x596A` / `0x64DC` / `0x65CE` 置位，`0x5FC0`（停机）清零 | `0x4946`（主循环） | **「本轮/本阶段已开始」**。四个置位点全在软定时回调里 |
| `+3` | `0x84358F` | 只有 `0x5FD8` 一处，且是**清零** | `0x43F4`（按键）、`0x46AA` | **「允许按键触发动作」**：与 `+6` 一起把按键分支短路 |
| `+6` | `0x843592` | `0x686` / `0x6B8`（都在启动段） | `0x66A` / `0x6A8` / `0x43EE` / `0x4688` / `0x4938` / `0x49DA` | **「输出锁定」**：非 0 时按键扫描跳过短按动作 |
| `+9` | `0x843595` | **未找到**（只被整块清零） | `0x494E` 一处 | 语义未知；只读一次，可能是停机时留痕 |
| `+0xB` | `0x843597` | `0x4418` / `0x4456`（按键）、`0x4994`（主循环）、`0x6632`（启动） | `0x46A4` / `0x4974` / `0x4982` / `0x662A` | **「长按已生效」**：按住超过 20 tick 置位，松手超过 20 tick 或长按 150 tick 后清零 |

`+9` 那一格是唯一没有写点的 —— 它只能被「整字节区间置零」清掉，找不到任何置 1 的地方，
所以**它在本固件里恒为 0**，那个读点也就永远是假分支。这比说「语义未知」更准确。

## 12. 主循环里那四个「粘合函数」的真身

主循环（§11）反复调 `0xADDC` / `0xADB8` / `0x7484` / `0x5060`。它们都不是应用逻辑，
而是**两个地基**：一个间接调用桩，一个外设/栈状态块的访问器组。

### 12.1 `0x5060` —— 4 字节的间接调用桩

```
0x5060  tjex r3      ; pc = r3
0x5062  tnop
```

两个调用点都先把指针装进 `r3` 再调它：

```
0x4B1A  r3 = u32[0x844BCC]   ; main 注册的第一个回调（0x0ED0 + 1 的 Thumb 指针）
0x4B1E  r0 = 67  r1 = 16  r2 = 0
0x4B24  tjl 0x5060
```

`0x4EB2` 那处同样先 `r3 = u32[0x844BCC]`，再传 `(128, 64)`。

⟹ `0x5060(a, b, c)` = **「经 RAM 里的函数指针调用」**。这解释了它为什么出现在主循环里却
自身没有任何动作；也说明主循环对上层是「可替换」的 —— 换掉 `0x844BCC` 就换掉了通知通道。

### 12.2 `0x5064` —— 命令分派器（入口地址订正）

之前所有文档写「分派函数 `0x506E`」，那是**序言第 5 条指令**；真实入口是 `0x5064`
（`0x5060` 那个桩之后的下一个 `tpush`）。本次已全局订正。

除已记录的 switch 外，开头还有两段 20 字节常量拷贝：

```
0x507E  从 0xCD54 拷 20 B 到 sp+0x30
0x509C  从 0xCD44 拷 20 B 到 sp+0x10
```

`0xCD54` = `90 5F 01 00` ×4 + `01 29 00 00`（90000, 90000, 90000, 90000, 0x2901），
`0xCD44` = 16 × `FF` + `90 5F 01 00`。这是编译器给栈上聚合做的 const 模板，
**目前没找到后续读取点**，先记着不下结论。

case 7 完整解码（此前只到「读 4 槽表」）：

```
r4 = 回包缓冲 + 3
for (i = 0; i < 4; i++) {
    slot   = 0x84355C + i*12
    if (u32[slot+8] == 0xFF) break       ; 空槽（首字节全 FF）
    buf[0] = u32[slot+8]                 ; 小时
    buf[1] = u32[slot+4]                 ; 分钟
    buf[2] = 0x1DC(u32[0x8435AC + i*4], 60)   ; 时长（秒） / 60
    r4 += 3
}
```

`0x8435AC` = `0x84355C + 0x50`，正是那个时长并行数组。⟹ 再次确认「槽位只存几点、
时长在并行数组」，且 `0x1DC` 确实是除法（不是硬件通道）。

### 12.3 `0xADDC` / `0xADB8` / `0xADC4` / `0xADD0` —— 一个结构体的四个单指令访问器

```
0xADB8(x)   byte[0x843C0C + 0x05] = x ; ret
0xADC4(x)   half[0x843C0C + 0x0E] = x ; ret
0xADD0()    return u32[0x843C0C + 0x2C]
0xADDC(x)   byte[0x843C0C + 0x04] = x ; ret
```

把全部调用点的实参扫出来（共 18 处）：

| 访问器 | 字段 | 实参 |
| --- | --- | --- |
| `0xADDC` | `+0x04` | `15` ×5（`0x46C2` / `0x486A` / `0x4AFE` / `0x4BDA` / `0x4D94`）、`3` ×1（`0x46D0`）、`0` ×5（`0x46EA` / `0x4D0A` / `0x6408` / `0x663A` / `0x6652`） |
| `0xADB8` | `+0x05` | `16`（`0x4636`、`0x4B02`）、`80`（`0x46B2`、`0x4F2C`）、`64`（`0x4EA0`） |
| `0xADC4` | `+0x0E` | `0`（`0x46E0`）、`3`（`0x46F0`） |

主循环里的规律（`--callsites 0xADDC` 可复现）：

- `15` 的 5 处全在「开始/进行」路径上，`0x4AFC` 那处是
  `0xADDC(15)` → `0xADB8(16)` → `0x7484(64,0,1)` → `[0x842F68+4] |= 8`；
  `0x4BDA` / `0x4D94` 两处也是先清状态、开寄存器再写 15。
- `0` 的 5 处全在收尾：`0x46EA`（按键收尾）、`0x4D0A`、以及存储/驱动段的
  `0x6408` / `0x663A` / `0x6652`。
- 长按路径 `0x46A0` 段：`0xADB8(80)` → `0x7484(64,0,1)` → `0xADDC(15)`。

`15` = `0b1111` 这个取值本身就说明 `+0x04` 更像**位掩码/档位**而不是枚举编号。

### 12.4 `0x7484(a, b, c)` —— 两处 8 位寄存器的位读写

```
m = a & 0xFF  （位掩码）
r0 = reg_read(a + 0x21)
b == 0 ? r0 |= m : r0 &= ~m
reg_write(a + 0x21, r0)

r0 = reg_read(a + 0x27)
c != 0 ? r0 |= m : r0 &= ~m
reg_write(a + 0x27, r0)
```

`reg_read` / `reg_write` 就是 `0x840` / `0x880`：`0x800643` 存旧值后清 0（临界区）、
把地址写 `0x8000B8`、把数据写 `0x8000B9`、往 `0x8000BA` 写 `0x40`（读）或 `0x60`（写）
再轮询忙位。所以这两个函数**不是** GPIO 数据口，是**模拟/外设寄存器访问**。

三个调用点全部是 `(64, 0, 1)`：`0x61` 与 `0x67` 的第 6 位置 1。
配套的上电序列在 `0x74EC(a)`：

```
reg 0x3C &= ~1 ; reg 0x2D = 0x15 ; reg 0x05 = 0x02 ; reg 0x2C = a | 0x1F
```

而主循环里另一个可疑的 `0x52C` 写的是 `0x800061 = 0x20`（同族寄存器的第 5 位）——
两者是同一套「外设组合开关」，此前把 `0x52C` 猜成「电源/复位序列」是接近的。

### 12.5 IRQ14 是 80 ms 超时监视

```
0x4618 (IRQ 14)
    if (byte[0x843960] != 8) return          ; 只在「已连接」状态下有效
    if (0x800740 - 0xADD0() > 0x138800)      ; 1,280,000 tick = 80 ms
        0xADB8(16)
```

`byte[0x843960] == 8` 与 Telink SDK 的 `BLS_LINK_STATE_CONN`（`BIT(3)`）取值一致，
强推断这是**链路状态字节**；`0x843C0C` 因此落在 BLE 栈全局区（`0x843900` 段）里。
`+0x2C` 就是「上次活动时刻」。

### 12.6 `0xADE8` / `0xAEC8`：预约 tick 中断

```
r3 = u32[0x843C0C + 0x34]          ; 基准 tick
r0 = u32[0x843B20 + 0x2C]          ; 偏移
r2 = r3 + (-56000) - r0 - [0x800740]
if (r2 > 0x3FFFFFFF) ...
u32[0x800744] = r3                 ; 系统 timer 的比较寄存器
u32[0x843C0C + 0x20] = r3 + u32[0x843B20 + 0x40]
```

`-56000` tick = **-3.5 ms**。`0x800744` 是系统 timer 的比较寄存器，写它等于
「到这个 tick 时触发中断」。同区的 `0x843A80`（`byte+11`、`half+0x1C` 在循环里递减）
和 `0x843B20` 是同一族上下文。

⟹ 这一层是**链路时序调度**，不是应用逻辑。

### 12.7 一个必须说清的矛盾

`0x843C0C` 的证据是**双向**的：

- **支持「链路层上下文」**：`0xAD8C`（它的初始化）紧跟 RF 初始化序列被调；
  IRQ14 以「已连接」为门；`0xADE8` 写 timer 比较寄存器；`x` 号实参 `16/64/80` 都在 RF 侧出现。
- **支持「应用侧执行器状态」**：主循环的起停序列直接写 `+0x04`（15/0），并且紧跟着
  `0x7484(64,0,1)` 这种寄存器开关；应用自身从不读回 `+0x04`。

两种解释都说得通，静态分析在这一层已到边界。

> **2026-11-08 补充（§13.7 已改写这个结论）**：把 `0xA000–0xB000` 整段读完之后，
> `0x843C0C` 既不是链路层上下文、也不是执行器状态，而是**定时 / 低功耗调度块**——
> 里面存的是定时到期时刻、唤醒比较基准、上次活动时刻和几个时长。
> 上面两个解读都不成立，`+0x04` 的具体语义仍开放。

## 13. `0xA000–0xB000`：调度与低功耗层

上一节把 `0x843C0C` 定性为「链路层上下文 or 执行器状态」二选一。把这一层整段读下来之后，
**两个都不对**：它是**定时 / 低功耗调度块**。下面按证据给。

### 13.1 区域地图（16 个入口）

| 入口 | 大小 | 静态调用者 | 定性 |
| --- | --- | --- | --- |
| `0xA014` | 80 | `0x4BE0` / `0x4CDE` / `0x4DCE` / `0xA312` | 向链路上下文 `0x843B20` 写一个字节（`+0x77`），返回 `0x80` / `0x3A` / `0`；未连接时直接返回 `0x80` |
| `0xA064` | 80 | `0xA492` / `0xA622` | 未细读 |
| `0xA0B4` | 4 | `0xA6CC` | `tjex r3` 桩 |
| `0xA0B8` | 1,540 | **无** | 本区最大的一块，入口是间接的 |
| `0xA6BC` | 212 | **无** | 由 `0x9A60` 注册（奇数指针 `0xA6BD`） |
| `0xA790` | 128 | `0xA882` / `0xAA82` | 未细读 |
| `0xA810` | 8 | **无** | 由 `0x9A48` 注册（`0xA811`） |
| `0xA818` | 520 | **无** | 未细读 |
| `0xAA20` | 344 | `0x2686` | **链路事件时序**（对 `0x843A80` / `0x843B20` 做 1.25 ms 单位的窗口计算） |
| `0xAB78` | 64 | `0x293A` | 未细读 |
| `0xABB8` | 372 | `0xAD3E` | 未细读 |
| `0xAD2C` | 188 | **无** | 由 `0x9A66` 注册（`0xAD2D`） |
| `0xAD8C` | 92 | `0x4752` / `0x4864` | **调度块初始化** |
| `0xADE8` | 214 | `0x2B6A` | **预约 tick 中断**（见 §13.5） |
| `0xAEC8` | 302 | `0x1E96` | 与前者同型 |
| `0xAF9C` | 4 | `0xAEE0` | `tjex r3` 桩（第三处） |

`0xAFA0` / `0xAFB0` / `0xAFBC` / `0xAFDC` / `0xAFE8` 是紧跟其后的 setter 群，§13.6 单列。

三处 `tjex r3` 桩（`0xA0B4` / `0xAF9C` / `0x2DF0`）加上主循环里的 `0x5060`，说明这套固件
**大量用品指针间接调用**，静态调用图天然会漏掉这些边。

### 13.2 `0x843C0C` 的字段表

| 偏移 | 类型 | 含义 | 证据 |
| --- | --- | --- | --- |
| `+0x00` | u32 | 初值 `0x2995`（10645） | `0xAD8C` 写；`0x1C6C` 判非 0 |
| `+0x04` | byte | **模式 / 掩码**，取值 `0` / `3` / `15` / `0x40` | `0xADDC` 写；`0xAFE8` 用 `== 0x40` 判等 |
| `+0x05` | byte | 取值 `16` / `64` / `80`，**未找到读者** | `0xADB8` 写 |
| `+0x0E` | half | 取值 `0` / `3`，**未找到读者** | `0xADC4` 写 |
| `+0x14` | u32 | **时长 A，单位毫秒**（内部 `×16000` tick） | `0xAFBC` 写；默认 `1,600,000` = 100 ms |
| `+0x18` | u32 | **时长 B，单位毫秒** | `0xAFBC` 写；默认 100 ms，初始化改 30 ms |
| `+0x1C` | u32 | **短时长，单位微秒**（内部 `<<4` tick） | `0xAFDC` 写；默认 `8000` = 500 µs，改 200 µs |
| `+0x20` | u32 | 基准 + 偏移（算出来的下次时刻） | `0xADE8` / `0xAEC8` 写 |
| `+0x22` | byte | **有定时挂起**（1 = 有，0 = 无） | `0xAFA0` 写 |
| `+0x28` | u32 | **下一个软件定时到期 tick**（0 = 没有） | `0xAFA0` 写，`timer_add` / `timer_poll` 调用它 |
| `+0x2C` | u32 | **上次活动时刻** | IRQ14 用它算超时 |
| `+0x34` | u32 | **基准 tick**，写进 timer 比较器 | `0xADE8` 写；`0x1E6C` 直接 `u32[0x800744] = u32[0x843C40]` |

`+0x14` / `+0x18` 的单位是算出来的，不是猜的：`0xAFBC` 里
`r2 = (a<<5) - a = 31a` → `r2 <<= 2` = `124a` → `r0 = r2 + a = 125a` → `r0 <<= 7` = **`16000a`**，
而 16,000 tick 正好是 1 ms。

### 13.3 定时钩子的注册链

```
main (0x7E2) → 0x437C()  →  0xAFB0(0x423D)       ; 0x423D = 0x423C + 1
                              └─ u32[0x844B48] = 0x423C   ; = timer_poll

协议栈 (0x2B14)：r3 = u32[0x844B48]
                 if (r3) 0x2DF0(1)               ; 0x2DF0 是 tjex r3 桩
```

⟹ `0x844B48` 是**定时轮询钩子**：应用注册，协议栈每轮调用。这也解释了 `0x423C`（timer_poll）
为什么没有普通静态调用者 —— 它只被存进这个槽。

### 13.4 `timer_poll` 的判决和两道阈值

```
0x423C
  now = [0x800740]; cnt = u32[0x842F34+0x30]
  if (cnt == 0) { 0xAFA0(0, 0); return }               ; 没有定时 → 报告"无挂起"
  if ((now + 0x800) - u32[0x842F34+4] > 0x3D08FFF) return
  逐槽遍历：deadline 已到就调 fn，并重排 deadline（interval << 4）
  ...
  r0 = u32[0x842F34+4]                                 ; 最早的 deadline
  if (r0 - now <= 0x02DC6BFF) 0xAFA0(r0, 1)            ; < 3 s 才报"挂起"
  else                        0xAFA0(0, 0)
```

两个阈值都有意义：`0x3D08FFF` = 0x3D09000−1 ≈ **4 s**，用来判「这个 deadline 是不是太久以前」；
`0x02DC6BFF` = 48,000,000−1 = **3 s**，只有下一个到期在 3 秒内才把唤醒挂上。
**这就是「睡之前决定要不要设定时器唤醒」的标准写法。**

### 13.5 tick 中断的预约

```
0x1E6C  u32[0x800744] = u32[0x843C40]      ; +0x34 → timer 比较器
        紧跟在写 0x800F01=1 / 0x800F20=0xFFFF / 0x800648 |= 0x100000 之后

0xADE8 / 0xAEC8
  r3 = u32[+0x34]
  r2 = r3 + (-56000) - u32[0x843B20+0x2C] - [0x800740]
  u32[+0x34] = r3 ; u32[+0x20] = r3 + u32[0x843B20+0x40]
  u32[0x800744] = r3                        ; 触发点
```

`-56000` tick = **-3.5 ms**，即「提前 3.5 ms 唤醒」。

### 13.6 六个 setter

| 函数 | 动作 | 调用点 / 实参 |
| --- | --- | --- |
| `0xAFA0(a, b)` | `u32[+0x28] = a`，`byte[+0x22] = b` | `0x41E6` / `0x42D2` / `0x435A`（`b=1`）、`0x42DE` / `0x4366`（`a=0,b=0`）——全部来自定时器代码 |
| `0xAFB0(a)` | `u32[0x844B48] = a` | `0x4380`，`a = 0x423D`（注册 timer_poll） |
| `0xAFBC(a, b)` | `u32[+0x14] = a ms`，`u32[+0x18] = b ms` | `0x4872`，`(50, 30)` |
| `0xAFDC(a)` | `u32[+0x1C] = a µs` | `0x487A`，`200` |
| `0xAFE8()` | 若 `byte[+0x04] == 0x40`：`0x800078 |= 0x100000`、`byte[0x80006F] = 0x80`；然后 `byte[0x8439C0] = 1` | `0x2A30` |
| `0x74EC(a)` | `reg0x3C &= ~1`；`reg0x2D = 0x15`；`reg0x05 = 0x02`；`reg0x2C = a \| 0x1F` | 外设上电序列 |

`0xAD8C`（初始化）就是把这套默认值铺一遍：

```
u32[+0x00] = 0x2995 ; half[+0x0E] = 0xFFFF
u32[+0x14] = u32[+0x18] = 0x186A00      ; 100 ms
u32[+0x1C] = 8000                        ; 500 µs
byte[+0x21] = 67
```

### 13.7 对 §12.7 的更新：结论改了

§12.7 当时把 `+0x04` 的两解读并列（链路层步骤号 vs 执行器使能）。本节证据推翻了**两个**：

- 同一个结构里存的是**定时到期时刻（`+0x28`）**、**唤醒比较基准（`+0x34`）**、**上次活动时刻（`+0x2C`）**、
  **两个毫秒级时长（`+0x14`/`+0x18`）**和一个微秒级短时长（`+0x1C`）；
- 写它的 `0xAFA0` / `0xAFB0` 全部来自**定时器代码**（`0x41xx–0x43xx`），读它的 IRQ14 做的是超时判断。

⟹ **`0x843C0C` = 定时 / 低功耗调度块**，不是执行器状态，也不是链路层上下文。
它是"应用和协议栈共用的调度基座"——这才是它同时被 RF 初始化和应用起停序列写的原因。

`+0x04` 则仍是开放的：取值 `0` / `3` / `15` / `0x40`，应用起停时写 `15` / `0`，
`0xAFE8` 又用 `0x40` 做等值判断。在低功耗语义下最自然的解释是
**「允许的唤醒源 / 睡眠等级掩码」**（`15` = 4 个源全开，`0` = 全关），
但**没有坐实**：要验证得在真机上让设备进入对应状态后测电流，或用调试器读该字节。

## 15. 第二轮补齐（ATT 层、事件分派、硬件除法器、引脚地图）

这一节全部来自新增的 `tools/tc32_ram.py`：它在每个函数内部线性传播常量寄存器，
把 `tloadr r3, [r6, #0x37]` 这种间接访问还原成绝对地址，于是「谁写谁读某个 RAM 字节」
变成一条可查询的事实。全文 602 个不同的 RAM/IO 目标、每目标带读写点数。

### 15.1 `0xA0B4`：真入口在 `0xA0B4`，是 ATT PDU 层

上一版说「`0xA0B8` 无入口」是**把序言的第三条指令当成了函数开头**（和早前 `0x506E` 那个错误同型）：

```
0xA0B4  tpush {r4, r5, r6, r7, lr}
0xA0B6  tmov  r7, r8
0xA0B8  tpush {r7}          ← 只是长序言的第二段
```

真入口 `0xA0B4` 有**唯一**一个静态调用者 `0xA6CC`，而 `0xA6CC` 在 `0xA6BC` 里；
`0xA6BC` 是一道门：

```
0xA6BC  if (u8[0x843BA0 + 0x37] != 0) return 0
0xA6CC  r0 = 0xA0B4(r0)     ; 门开着才往下走
```

`0xA0B4` 收到的是请求描述符：`[r0+4]` 数据基址、`[r0+5]` 类别、`[r0+6]` 长度，
然后按 `u8[buf+1]` 分派 —— **和 §6 那张 `0xD104` 表是同一套 ATT 操作码**：
4/5/7/8/11/12/13/17/18/19/22 各有 case，19 直接返回，18 走 `0xA66A`，22 走 `0xA600`。

其中 `0xA508` 那支是 **MTU 交换**，读得最清楚：

```
r0 = (u8[buf+4] << 8) | u8[buf+3]
if (r0 > 26 && r0 <= 251) { ... } else 返回 0x306
... if (r2 > 100) r2 = 100        ; ← MTU 上限钳到 100
u16[ctx+0] = r0 ; u16[ctx+2] = r2
u8[ctx+17] = 2
```

「钳到 100」与真机实测帧 `BD 0E 02 … 64` 里的 `0x64` 完全对上。
所以 `0x7A98`（§6）与 `0xA0B4` 是一上一下两层：**`0x7A98` 按 opcode 找应用处理，
`0xA0B4` 做 PDU 的拆装与链路状态推进**。

### 15.2 `0xB874`：LL / RF 事件分派器（表 A 的真正使用者）

`0xB874` 才是 `0xD31C` 那张表的读者（literal 在 `0xBB80`）：

```
0xB874  r5 = r0                        ; 事件码
        if (r0 > 14) goto 0xB882
0xB8A6  r3 = r0 << 2 ; pc = u32[0xD31C + r3]
```

它有 11 个调用者，传入的事件码是 **2、3、4、6、7、8、9、10、11、13**。
每个 case 都做两件事：读一次 `0x800740`（系统 tick）当时间戳、往 `0x843CEC` 记一条事件
（`+1` 类型、`+4` 长度、`+5`、`+6` 事件码）。case 指纹：

| slot | 目标 | 特征 |
| --- | --- | --- |
| 0, 1 | `0xB882` | 只记事件、返回 `0x843CEC` |
| 2 | `0xB8D6` | `u8[0x8439CC]=1`，读 RF 状态，memcpy |
| 3 | `0xB900` | 5 次 memcpy + 调 `0xC604` |
| 4 | `0xB99E` | memcpy + `0x843D6C` |
| 5 | `0xB9E0` | 只记事件 |
| 6, 7 | `0xB9FE` / `0xBA24` | memcpy + `0x843D1C` |
| 8 | `0xBA58` | 调 `0x1F84` / `0x684C` / `0x7224`，碰 `0x843DA8` |
| 9 | `0xBA9A` | `0x8439EC` / `0x84392A` |
| 10 | `0xBADC` | `0x843DB8` |
| 11 | `0xBB00` | 只记事件 |
| 12 | `0xBB22` | **递归调 `0xB874` 五次**，批量处理 |
| 13, 14 | `0xB8AE` | 把 `u32[0x800740] | 1` 存进 `0x843D70`，再调 `0xBBCC` |

`0x843D70` 全固件 16 写 1 读 —— 是一个「最近一次 RF 状态快照」。
`0x800740` 在 13 个 case 里各读一次，说明它是 tick，不是中断标志。

### 15.3 `0xABB8` 有入口，而且 `0x84391C` 是个函数指针

上一版把 `0xABB8` 列进「无入口」，其实 `0xAD3E` 就是它的调用者。它是**链路参数初始化**：

```
if (u32[0x843920] & 0x10) {
    u32[0x843920] &= ~0x10
    u8[0x8439CC] = 0
    u16[0x843944] = 27 ; u16[0x843946] = 27
    u8[0x843944+18] = 0 ; u8[0x843944+19] = 0
    u8[0x843A7C] = 0
    cb = u32[0x84391C]                 ; ← 函数指针
    if (cb) { cb(0x40, 0x843B20+13) ; cb(4, 0x843B20+13, u32[0x84395C], 1) ; ... }
}
```

`0x84391C` 里存的是 **Thumb 函数指针**，调用形式是 `tjl 0xAD28`（`tjex r3` 桩），
这就是「间接调用查不到」的一类来源：**先 `tloadr r3,[pc]` 取指针，再走 `blx r3` 桩**。
同型的还有 `0xAA1C`、`0xAF9C`、`0x5060`、`0x2DF0`、`0xA6B8` 五处。

> 订正：`tjex r3` 桩一共 **6** 个（`0x5060`、`0x2DF0`、`0xA6B8`、`0xAD28`、`0xAF9C`、`0xAEC4`），
> 上一版把 `0xA0B4` 也算进去了 —— 那是 `tpush`，不是桩。桩的形态固定为 `tjex r3` + `nop`，
> 代码里以 `tjl 桩地址` 的形式当 `blx r3` 用。

### 15.3b `0x9A18`：栈回调注册表 —— 所有「无静态入口」的答案

`0x9A18` 这一个函数连写七个全局，存的全是**奇数（Thumb）函数指针**：

| 全局 | 存入 | 被谁取用 |
| --- | --- | --- |
| `0x843A70` | `0xA811` | `0x941C` |
| `0x8439B0` | `0x9DBD` | `0x19A6` |
| `0x843964` | `0x27F9` | 无直接取用点 |
| `0x8439AC` | `0x26E5` | `0x1940` |
| `0x8439B8` | `0xA6BD` | 无直接取用点 |
| `0x8439BC` | `0xAD2D` | `0x1BBE` |
| `0x843AD8` | `0x9E09` | `0x8CD8` / `0x8EF4` / `0x9932` / `0x99B0` |

所以 `0xA810`（524 B）、`0xA6BC`、`0xAD2C` 都不是「死代码」，而是**注册给栈的回调**，
调用点只能是 `tjl` 到 `tjex r3` 桩再 `bx` 过去 —— 这就是为什么纯静态 `tjl` 图里它们入度为 0。

同一个函数还顺带初始化了链路上下文：`u16[0x843B20+0x12] = -1`、
若 `u8[0x8435D8+1] != 0` 则 `u32[0x843B20+0x68] = 150<<4 = 2400`。

### 15.3c `0x9E08`：发送队列入队

上面表里 `0x843AD8` 那个回调，本体是 `0x9E08`（全固件 17 个直接调用者，
`0xA0B4` 里就调了 4 次）。它做的事很明确：

```
r5 = u8[0x800643] ; u8[0x800643] = 0        ; 关中断，存旧值
r6 = (u8[0x843508+6] - u8[0x843508+7]) & 31 ; 环形队列已用槽
idx = ((u16[0x843508+4] - 1) & u8[0x843508+6]) * u32[0x843508]
dst = 0x843288 + idx + 4
memcpy(dst, r1, u8[r1+1] + 2)               ; 长度字节 + 2 = 帧长
u8[0x800643] = r5                            ; 恢复中断
```

即 **把 `r1` 指向的一帧（首字节是长度）拷进 `0x843288` 的环形 TX 队列**。
`0x800C2A/0x800C2B` 是 RF 的 DMA 读/写指针，队列余量就是拿这两个算的。

⟹ `0xA0B4` 的「构造 ATT 响应 → `0x9E08` 入队」这条链闭合了。

### 15.4 `0x1D0/0x1D4/0x1D8/0x1DC`：硬件除法器

四个地址是**同一个函数体的四个入口**，只差一条 `tmov r2, #0..3`：

```
0x1D0  r2 = 3   0x1D4  r2 = 1   0x1D8  r2 = 2   0x1DC  r2 = 0
                 ↓
0x1E0  r3 = tmrcs ; r3 |= 0x80 ; tmcsr r3      ; 临界区
       u32[0x800664] = r0                      ; 操作数 A
       u32[0x800668] = r1                      ; 操作数 B
       u8 [0x800660] = r2                      ; 操作码 = 启动
       while (u8[0x800660] != 0) ;             ; 忙等归零
       return (r2 <= 1) ? u32[0x800668] : u32[0x800664]
```

`0x800660` 是启动/状态，`0x800664` 与 `0x800668` 是操作数兼结果。
商和余分别落在两个寄存器，所以 0/1 取一个、2/3 取另一个。

用 `0x5CB0` 那个调用点可以定性（把秒拆成天/时/分/秒）：

```
r5 = div1DC(secs, 86400)     ; 天      → 商
r4 = div1D8(secs, 86400)     ; 当天秒数 → 余
r0 = div1D8(r4, 60)          ; 秒      → 余
r4 = div1DC(r4, 60)          ; 分      → 商
if (r0 > 59) 出错
```

⟹ **`0x1DC` = 商、`0x1D8` = 余**（`0x1D4`/`0x1D0` 是对应的另一个符号性变体）。
全部调用点用到的除数只有 10、37、60、100、200、250 —— 都是单位换算。

### 15.5 ⚠️ `0x800540` / `0x800548` 是**真随机数发生器**，不是 GPIO

上一版把这一对当成「消杀/UV 引脚」，**是错的**。`0xC80C` 把它用得一清二楚：

```
u8[0x800540] = 0
if (u8[0x800540] & 0x40000000) { ... }
while ((u8[0x800540] & 4) == 0) ;          ; 等数据就绪
r2 = u32[0x800548] ; store x4              ; 连读 4 个字 = 16 字节
... 与缓冲 XOR 混合 ...
```

写 0 复位、轮询就绪位、连读四个字做熵池混合 —— 这是 TRNG 的标准用法。
`0xC7AC` 里同样是连读 4 次 `0x800548`。所以这一对要整体改判：**`0x800540` = TRNG 控制/状态，
`0x800548` = 32 位随机数据**。

### 15.6 真正的 GPIO 地图

| 端口 | 寄存器 | 观测到的访问 |
| --- | --- | --- |
| P0 | `0x800580` in / `0x800581` ie / `0x800582` oen / `0x800583` out / `0x800584` ds | `in` 用于按键（bit6） |
| P1 | `0x800588`…`0x80058B` out | `0x80058B` 1 处 |
| P2 | `0x800590`…`0x800593` out | `0x800593` **12 处**（多为 `&= ~0x10`，bit4） |
| P3 | `0x800598`…`0x80059B` out | `0x80059B` **26 处**（全固件最热的执行器口） |

P3 的 26 处分布在 13 个函数里，形态一律是「读-改-写」：`tloadrb → tbclr/tbor → tstorerb`。
确定的位：

| 位 | 证据 | 推断用途 |
| --- | --- | --- |
| bit2 | `0x5FD0` 停机时 `0x80059B &= ~4` | 执行器 1（停机必关） |
| bit4 | `0x4B98` / `0x4D82` / `0x5FCC` 三处 `tbclr #16` | 执行器 2（三处关机路径都会关） |
| bit7 | `0x4DD4` 附近 `0x80059B |= 0x80`；`0x4B60` 与 `0x5F94` 关机时清 | 执行器 3（与 bit2 成对） |

P0 bit6 = 按键输入（`0x43A0` 里 `tand 0x40`），这一点与上一版一致。

### 15.7 还有两个小事

- `0x2F8C`（代码 A 的末尾）不是填充，是 ASCII **`Hi-YM01-12DC2110000`** —— 产品型号串，
  后面紧跟 4 KiB 近零区里嵌的小表（`0x327C`：`0x40`、`8`、`0x84307C`，像 `.data` 拷贝描述符）。
- `0x843C0C` 的 `+0x00` 在 `0xAD90` 被写成 **`0x2995`**，同处还写 `+0x0E = -1`、
  `+0x14`/`+0x18` = `0x186A00`（1,600,000）。这说明它是**结构体起点**而不是指针变量
  （`0x1C6E` 只把它当「非零即已初始化」用）。

## 16. 还不知道的

第二轮把上表的 8 条清掉了（`0xA0B4`/`0xA818`/`0xABB8`、`0xD31C` 入口、`0x1DC`、五个子标志、
GPIO 归属、`0x3000` 空洞）。剩下这些，基本都要靠真机或调试器才能推进：

- `0x1A0` 那个第二入口（头部 `0x10` 指向它）：本体是**中断上下文保存/恢复 + `treti`**，
  见 §9，但它是给哪个 IRQ 用的仍未定。
- `0x0ED0` / `0x1378` / `0x7520` / `0x13E8` 四个回调分别处理什么事件。
- `0x6538`（被 `0x5F90` 与主循环反复取消的那个定时回调）是干什么的。
- `0x843C0C` 的 `+0x04` 到底是不是「唤醒源/睡眠等级掩码」（§13.7）；
  `+0x05` 的 `16/64/80`、`+0x0E` 的 `0/3`、`+0x21` 的 `0x43` 分别是什么。
  这一组只能靠**真机测电流**或调试器读内存。
- `0x84358C` 的 `+9` 恒为 0 已经说清，但 `+2` 的四个置位点分别属于哪条业务路径还没串起来。
- `0x5064` 开头从 `0xCD44` / `0xCD54` 拷进栈的两块 20 字节常量，后面谁在读。
- `[0x844B98]` 由谁写：同区域的 `0x844B94` 有一个 32 位读-改-写点（`0x4BF0` / `0x4BFC`），
  但 `0x844B98` 本身仍只有两处读（`0x490E` / `0x4922`）、零处写，只能在真机上读内存验证。
- `0x52C`：写 `0x800061 = 32` 再写 `0` 是一次复位/触发序列，随后等 `0x800740` 走完 400 tick，
  再清 `0x843534` 结构的前 8 个字并写 `0x800B08`。定性为「日志区复位 + 外设触发」，但
