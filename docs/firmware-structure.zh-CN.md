# 原厂固件功能结构（反汇编）

> 2026-11-08。承接 [固件静态分析](firmware-analysis.zh-CN.md)，这次把 `0x00000–0x0D3E4` 的代码真正反汇编了。
> 工具：[`tools/tc32_disasm.py`](../tools/tc32_disasm.py)，纯 Python 标准库。
> 复现：`python tools/tc32_disasm.py --functions --xrefs --tables`；看某段代码用 `--range 50ac:50e8`。

## 0. 方法，以及为什么不用现成 objdump

Telink IDE 自带的 `tc32-elf-objdump.exe` 在本机缺 3 个 2010 年前后的 MinGW 运行库
（`libgcc_s_dw2-1.dll`、`libgcj-13.dll`、`libintl-8.dll`），启动即 `0xC0000135`；
Ghidra 又需要 Java，本机也没有。

但 [trust1995/Ghidra_TELink_TC32](https://github.com/trust1995/Ghidra_TELink_TC32) 仓库里的
`generate_sleigh.py` 保存了**从官方 objdump 提取的完整 opcode 表**（62 条 16 位 + 2 条 32 位，
含 value/mask 与汇编格式串），`.slaspec` 里给出了分支位移和 PC 相对加载的计算式。
据此写了一个纯 Python 解码器，**无外部依赖、可复现**。

**解码可信度**：26,056 条指令，仅 53 条未定义（覆盖率 **99.80%**）；
982 个 `tjl` 调用点解出 290 个目标，**全部落在 `0x0–0xD3E4` 且偶数对齐**；
literal pool 解出的地址绝大多数是 `0x800xxx`（寄存器）或 `0x84xxxx`（RAM），符合 TLSR8258 内存映射。
相比之下标准 ARM Thumb 解码器（Capstone）在同一区域解出的指令分布和纯数据区没有区别 —— 见静态分析 §2。

关键公式（来自 `.slaspec`）：条件/短跳转 `target = addr+4 + 2*sext(disp)`；
32 位调用 `target = addr+4 + (disp1<<12) + 2*disp2`，`lr = addr+4`；
literal 地址 `((addr+4)&~3) + 4*imm8`。

操作数直接由格式串里的位域还原（`%0-2r` = bit0–2 的寄存器、`%6-10d` = bit6–10 的立即数、
`%D/%S` 的高位在 bit7/bit6、`tpush` 列表 = bit0–7 + bit8=lr、条件码 = bit8–11），
所以反汇编输出可读，能直接看 `tmov r1, #219`（= `0xDB`）这类常量和 `[r6, #2]` 这样的偏移。

## 2. 函数规模与调用图

- **290 个直接调用目标**（`tjl`/`tjlex`）+ **278 个 `tpush` 序言** → 合并后约 **386 个函数入口**，
  中位间隔 56 B，最大的间隔 2,218 B。
- 最热的几个（被调次数）：`0x0880`(122)、`0x7214`(78)、`0x0840`(77)、`0x0A40`(25)、`0x09A4`(18)。
  `0x0880`/`0x0840` 都访问 `0x800643`(IRQMODE) 和 `0x8000B8/BA`，是典型的**开关中断的临界区helper**；
  `0x7214` 只有 7 条指令却被调 78 次，是小工具函数。
- 最大的函数 `0x2EA0` 约 2,224 条指令，含 `0xBD` 常量，推测是主状态机 / BLE 事件主处理（未证实）。
- **34 个入口完全不在直接调用集合里**（11 + 23）：它们只通过下面两张函数指针表间接调用，
  是目前功能标注最大的空白。

### 3.1 完整命令表

分派函数 `0x5064` 取 `frame[0]` 判帧头（`0xDB`）、取 **`frame[2]`** 作命令字，
用二分比较树散开。所有回包都写进固定缓冲 `0x844ACC`：`[0]=0xBD`、`[1]=长度`、
`[2]=命令字原样回抄`。每张分支表都已在真机验证过（见 [protocol §3.6](protocol.zh-CN.md)）。

| cmd | 处理函数 | 行为 |
| --- | --- | --- |
| `00` `01` | `0x5224` | 未实现，回 `BD 01 00 xx` |
| `02` | `0x5438` | 状态查询 + 写对时 |
| `03` | `0x5424` | 电量（RAM `0x8435A0`） |
| `04` | `0x555A` | 立即开关 / 设置定时 |
| `05` | `0x551A` | 读一条日志（`0x5AFC`） |
| `06` | `0x5536` | ACK（`0x5BA4`）后取下一条 |
| `07` | `0x50F6` | 读 4 槽定时表（3 B/槽） |
| `08` | `0x51A4` | 写定时表（先 `0x604C` 解析） |
| `09` | `0x5242` | 读序列号块 `0x43000` |
| `A0` | `0x5382` | **恢复出厂**：`0x5C18` 擦日志/配置/索引三扇区 + `0x5F90` 重置 RAM 状态 |
| `A2` | `0x52F2` | MAC 读写（写仅在现存 MAC 为 `FF×6` 时） |
| `A3` | `0x53DC` | 序列号，块空则写入 |
| `A4` | `0x564E` | 版本字面常量 `"000014"` |
| `A5` | `0x566A` | 只读 MAC |
| `A6` | `0x5182` | 擦 `0x44000` + 写 `01` |

`EC` 不是命令：它出现在 `0xEC<<11 = 0x76000`（校准/MAC 扇区）的地址拼接里，
`86`（`0x43000` 序列号块）、`88`（`0x44000` 标记扇区）、`80`/`82`/`84`/`8A`/`8C`
同理，都是扇区号。`3C` 也不是命令：它是 `0x514E` 传给 `0x1DC` 的**第二个参数 60**，
用来把槽位里的时长（秒）换算成回包第 3 字节（分钟）。

### 3.2 flash 数据布局（由地址拼接点反推，已用镜像核对）

| 偏移 | 内容 | 证据 |
| --- | --- | --- |
| `0x40000` | 日志表 200 槽 × 8 B = 1600 B（时间戳[4] 大端・时长[2]・类型[1]・`0xFF`） | `0x59C2` 整扇区读-改-写 |
| `0x41000` | 配置：`02 00 00 00 | B4 0F | 2C 01 00 00 …`（2 条定时、4020、300） | `0x453A`、`0x5C32` |
| `0x42000` | 4 字节持久值（实测 `55`） | `0x5924`/`0x5934` |
| `0x43000` | 16 字节序列号串（出厂为空，`FF×16`） | `0x5242`/`0x53E4`/`0x5834` |
| `0x44000` | 标记扇区，`A6` 擦写目标（出厂全 `FF`） | `0x518E`/`0x5196` |
| `0x45000` | **1 字节日志队列索引**：追加 +1、ACK −1、`0xFF` = 空 | `0x59D0`/`0x5B36`/`0x5BE2` |
| `0x46000` | 4 字节时间戳（实测 `6AEFE8EE`，与最新日志一致） | `0x592C`/`0x5940` |
| `0x76000` | 8 字节校准：前 6 字节反序即 MAC | `0x5300`/`0x5674` |

RAM 侧的状态块从 `0x84355C` 起（`0x5F90` 初始化，`0x5382`/`0x5438`/`0x51A4` 都在用）：

| 偏移 | 内容 |
| --- | --- |
| `+0x00…+0x2F` | 4 槽 × 12 B：`+4` = 分钟（4 B）、`+8` = 小时（4 B），其余字段未定 |
| `+0x30` | 状态字（`0x84358C`，`[1]` 是 `A0` 的分流标志） |
| `+0x3C` | **当前周期时长（秒）**（结束时的日志时间戳 = `+0x48 − +0x3C`，见代码结构图 §8） |
| `+0x40` | 本周期已运行秒数（1 Hz 自增） |
| `+0x48` | **当前秒计数**（`0x8435A4`，1 Hz 自增；状态查询也会写） |
| `+0x4C` / `+0x53` | 单字节标志（`0x5F90` 置 `2`；触发类型从这里读进日志记录） |
| `+0x50…+0x5F` | **4 个 32 位时长（秒）**，与上面的槽位一一对应 —— 时长不在槽位里 |

⟹ 槽位只管「几点」，时长是并行数组；出厂默认是 `08:00`/`20:00` 各 `180 s`（= 3 分钟）。

日志是**栈式**的：追加写 `index+1`、确认写 `index-1`，所以消费顺序是**从最新一条往回**，
`0xFF` 表示空队列。**确认只改这一个字节，不擦记录** —— 这就是 45 条确认完之后
200 槽历史仍完整留在 flash 里的原因。追加一次要重写整块 1600 B（读-改-写整个扇区），
所以擦写次数按「每条记录一次扇区擦写」计。

## 4. 两张 switch 跳转表

两张都是 `switch` 的跳转表，**不是回调注册表**（2026-11-08 更正，详见[代码结构图](firmware-code-map.zh-CN.md) §6）。

- **`0xD104`**：83 槽、13 个真实 case，其中 **70 槽指向 `0x7AF2`** —— 而 `0x7AF2` 就是
  `r6 = 0; return r6`，即 `default: return 0`。13 个 case 值与 ATT 操作码逐个吻合，
  因此这是 **ATT 请求分派器**（`0x7A98`），入口是 `0x8D04`。
- **`0xD31C`**：上一版把它当成「一张 30 槽的表」，**实际是两张 15 槽的表背靠背**。
  `0xB8A6` 之前是 `tcmp r0, #14` + `tjls`，索引只可能 0..14，所以它只覆盖 `0xD31C–0xD357`；
  `0xD358` 有自己的 literal（`0xC034`），是第二张同样 15 槽的表。两张表都以 `0xBCA6` 兜底。
  分派器 `0xB8A6` 属于 `0xB874`（LL/RF 事件分派，11 个调用者传事件码 2..13），
  详见[代码结构图](firmware-code-map.zh-CN.md) §15.2。
- 这两张表的 case 合计就是上一版记的「34 个间接入口」，它们**不出现在 290 个 `tjl` 目标里**，
  所以只靠静态调用图会漏掉这层代码 —— 但它也不是「注册的回调」，而是编译器生成的 `switch` 展开。

## 5. 硬件寄存器使用（对照 TLSR8258 datasheet）

| 地址 | 含义 | literal 引用 / 涉及函数 |
| --- | --- | --- |
| `0x800740` | `SYS_TIMER0`，16 MHz 系统 tick | 89 次 / 40 个函数 —— 所有延时、超时、软定时 |
| `0x800744` | system timer 区 | 16 次 / 11 个函数 |
| `0x800643` | `IRQMODE`，全局中断使能 | 32 次 / 22 个函数 |
| `0x800640`–`0x642` | 中断掩码 | 见各函数 literal |
| `0x800540` / `0x800548` | **TRNG 控制/状态 + 32 位随机数据**（不是 GPIO） | 各 21 处；`0xC80C` 写 0、轮询 bit2、连读 4 个字做熵池 |
| `0x800580`–`0x800583` | P0 in / ie / oen / out | `0x800580` 7 处（按键 bit6） |
| `0x80058B` | P1 out | 1 处 |
| `0x800593` | **P2 out** | 12 处，多为 `&= ~0x10` |
| `0x80059B` | **P3 out** | **26 处 / 13 个函数** —— 全固件最热的执行器口 |
| `0x800660` / `0x800664` / `0x800668` | **硬件除法器**：启动、操作数 A、操作数 B | `0x1E0`，四个入口 `0x1D0/1D4/1D8/1DC` 分别是商/余 |
| `0x800F00` / `0x800F20` | 未查明（疑似 RF/analog/flash 控制） | 8 / 16 次 |
| `0x80000C` / `0x80000D` | 未查明 | 12 / 20 次 |

literal pool 的 1,688 个引用按目标分类：RAM `0x84xxxx` 867 次、IO 寄存器 384 次、
代码/常量 176 次、其它 251 次。**没有任何一次直接指向 `0x40000` 日志区或 `0x76000` 校准区**。

## 6. 新发现（协议文档与静态分析里都没有的）

1. **56 字节无结构常量块 `@0xD2A8–0xD2E0`**：`64 10 b7 1d … 78 e2 0a a0`，51 个不同字节值、
   熵 5.63（代码区 `0xCC00` 为 5.93，**熵本身不能证明是加密材料**）。位置夹在配置常量与函数指针表之间，
   疑似 BLE 安全/随机相关常量，**用途未证实**，不要当成密钥或后门。
2. **两张 switch 跳转表**（§4；原先记成「函数指针表 + 34 个间接入口」，已更正）。
3. **`0x3000–0x3FFF` 4 KiB 区在整个固件里没有任何代码引用**（0 调用、0 literal），
   比"低熵数据表"更可能是保留/校准扇区。
4. 命令分发与回包构造的确切地址（§3）；**整张命令表与 flash 数据布局**（§3.1、§3.2）——
   其中 `03`（电量）、`09`（序列号块）、`A6`（擦标记扇区）是协议文档里从未出现过的。
5. 主循环里四个「粘合函数」的真身（见[代码结构图](firmware-code-map.zh-CN.md) §12）：
   `0x5060` 是经 RAM 指针调用的 4 字节桩、`0x5064` 才是命令分派入口（订正旧记的 `0x506E`）、
   `0xADDC` / `0xADB8` / `0xADC4` / `0xADD0` 是 `0x843C0C` 结构四个单指令访问器、
   `0x7484` 是模拟/外设寄存器的位读写。同一轮还把这个结构定性为
   **定时 / 低功耗调度块**（`+0x28` = 下一个软件定时到期、`+0x34` → timer 比较器、
   `+0x14`/`+0x18` = 两个毫秒时长），见 §13。
6. `0x800740` 系统 tick 被 40 个函数使用 —— 说明大量逻辑是基于 tick 的软定时，
   与「对时后按 Unix 秒调度、未对时用 1970 起秒数」的观察相容。

## 7. 还不知道的

- 向量表 64 × `0x06C0` 的确切语义；头部 `0x0C` 字段；原厂尾部校验算法。
- `0xD2A8` 无结构常量块、`0x3000` 近全零区的用途。
- `0xD358` 那张表 B 的使用者函数（literal 在 `0xC034`）还没逐个 case 标注；`0x2EA0` 那个 2,224 条指令的大函数是不是主循环。
- `0x1DC` 的真实身份：它把两个参数写进 `0x800664`/`0x800668` 并轮询 `0x80065C`，
  行为像"硬件通道 + 等待"，但结果确实等于 `被除数 / 60`（槽位时长秒 → 分钟），尚未定性。
- `0x842F34` 那个 3 项软定时器数组（`0x41B4`）里的 `0x6309` / `0x6539` 两个事件分别代表什么
  （`0x5F90` 会先取消它们，`0x41B4` 重新装载，间隔 `0x0F4240`）。
- `0x800Fxx`、`0x80000C/D` 寄存器用途；消杀/UV 具体由哪个 GPIO 驱动。
- 没有符号表，所有函数只能按地址和引用关系标注，无法自动命名。
