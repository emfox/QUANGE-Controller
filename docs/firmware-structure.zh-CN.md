# 原厂固件功能结构（反汇编）

> 2026-11-08。承接 [固件静态分析](firmware-analysis.zh-CN.md)，这次把 `0x00000–0x0D3E4` 的代码真正反汇编了。
> 工具：[`tools/tc32_disasm.py`](../tools/tc32_disasm.py)，纯 Python 标准库。
> 复现：`python tools/tc32_disasm.py --functions --xrefs --tables`；看某段代码用 `--range 50ac:50e8`。

## 0. 方法，以及为什么不用现成 objdump

Telink IDE 自带的 `tc32-elf-objdump.exe` 在本机缺 3 个 2010 年前后的 MinGW 运行库
（`libgcc_s_dw2-1.dll`、`libgcj-13.dll`、`libintl-8.dll`），启动即 `0xC0000135`；
Ghidra 又需要 Java，本机也没有。

但 [trust1995/Ghidra_TELink_TC32](https://github.com/trust1995/Ghidra_TELink_TC32) 仓库里的
`generate_sleigh.py` 保存了**从官方 objdump 提取的完整 opcode 表**（62 条 16 位 + 2 条 32 位，
含 value/mask 与汇编格式串），`.slaspec` 里给出了分支位移和 PC 相对加载的计算式。
据此写了一个纯 Python 解码器，**无外部依赖、可复现**。

**解码可信度**：26,056 条指令，仅 53 条未定义（覆盖率 **99.80%**）；
982 个 `tjl` 调用点解出 290 个目标，**全部落在 `0x0–0xD3E4` 且偶数对齐**；
literal pool 解出的地址绝大多数是 `0x800xxx`（寄存器）或 `0x84xxxx`（RAM），符合 TLSR8258 内存映射。
相比之下标准 ARM Thumb 解码器（Capstone）在同一区域解出的指令分布和纯数据区没有区别 —— 见静态分析 §2。

关键公式（来自 `.slaspec`）：条件/短跳转 `target = addr+4 + 2*sext(disp)`；
32 位调用 `target = addr+4 + (disp1<<12) + 2*disp2`，`lr = addr+4`；
literal 地址 `((addr+4)&~3) + 4*imm8`。

## 1. 代码 / 数据布局

| 范围 | 性质 | 证据 |
| --- | --- | --- |
| `0x000–0x027` | 固件头 | 长度字段 `0x18`，见静态分析 |
| `0x028–0x0A7` | 64 × 半字 `0x06C0` | 解出来是 `tmov %D,%S`；作为向量表语义未定 |
| `0x0A8–0x2FFF` | 启动 + Telink SDK 库代码 | 调用/literal 密集，0 个空白页 |
| **`0x3000–0x3FFF`** | **4 KiB 近全零区** | **0 个调用点、0 个 literal 引用**，不是代码 |
| `0x4000–0x6FFF` | 应用层：广播、BLE/GATT、命令处理 | 调用密度最高的区段，见 §3 |
| `0x7000–0xCBFF` | 应用逻辑 + SDK（含事件处理函数） | 均匀的代码密度 |
| `0xCC00–0xD0FF` | 广播/名字/GATT 属性数据与引用它的代码 | 静态分析 §3 |
| `0xD104–0xD24C` | **事件回调表**，83 项 | 见 §4 |
| `0xD250–0xD2E4` | 配置常量 + **56 B 无结构常量块** | 见 §6 |
| `0xD31C–0xD390` | **跳转/分派表**，30 项 | 见 §4 |
| `0xD3A4–0xD3E4` | 字符串、常量、4 B 校验尾 | — |

## 2. 函数规模与调用图

- **290 个直接调用目标**（`tjl`/`tjlex`）+ **278 个 `tpush` 序言** → 合并后约 **386 个函数入口**，
  中位间隔 56 B，最大的间隔 2,218 B。
- 最热的几个（被调次数）：`0x0880`(122)、`0x7214`(78)、`0x0840`(77)、`0x0A40`(25)、`0x09A4`(18)。
  `0x0880`/`0x0840` 都访问 `0x800643`(IRQMODE) 和 `0x8000B8/BA`，是典型的**开关中断的临界区helper**；
  `0x7214` 只有 7 条指令却被调 78 次，是小工具函数。
- 最大的函数 `0x2EA0` 约 2,224 条指令，含 `0xBD` 常量，推测是主状态机 / BLE 事件主处理（未证实）。
- **34 个入口完全不在直接调用集合里**（11 + 23）：它们只通过下面两张函数指针表间接调用，
  是目前功能标注最大的空白。

## 3. 能定位到的功能锚点

| 功能 | 地址 | 证据 |
| --- | --- | --- |
| **帧头校验 + 命令分发** | 函数 `0x506E`，核心 `0x50AC–0x5560` | `0x50AC tmov #0xDB` → 不等跳 `0x50CA` → `0x50CC tmov #0xBD` → `0x50D0` 起一串 `tmov #cmd; tcmp; tj` 的 switch |
| **回包构造** | `0x6A34`（4 × `tmov #0xBD` 分支） | 另有 `0x0B28`、`0x6144`、`0x648A`、`0x9AAC` 等 BD 点 |
| 广播数据 | `0x47D2`→`0xCD00`(SCAN RSP)、`0x4804`→`0xCCEC`(ADV)、`0x4D10`→`0xCCE4` | literal pool 引用 |
| GATT 属性表 | `0x507E`、`0x509C`、`0x530E`、`0x58E6` | 指向 `0xCD44`/`0xCD54`/`0xCDB4`/`0xCDC8` |
| 厂商串 `LFWY020702/` | `0x569C`、`0x5848` | 指向 `0xD098` |
| 十六进制表 | `0x122` | 指向 `0xD3A4` |
| **日志区 `0x40000`** | **没有找到任何 literal 直接引用** | 见 §7 |

命令分发函数里出现的立即数（可与协议文档对照）：
`DB BD 08 04 06 03 07 00 01 02 05 09 0B 0D 0E 0F 10 11 19 3C 86 88 A0 A2 A3 A5 A6 EC`。
其中 `0xDB/0xBD` 是帧头，`00 01 02 04 06 08` 与已知命令码吻合。
**`A0/A2/A3/A5/A6` 已在真机上确认为 `DB 01 Ax` 设备信息查询**：`A2`/`A5` 回 MAC、
`A3` 回 `LFWY020702/` + 6 字节、`A4` 回版本 `"000014"`、`A6` 回空包，
详见 [protocol §3.5](protocol.zh-CN.md)。`EC/86/88/3C` 仍未验证。

## 4. 两张函数指针表

- **`0xD104` 事件回调表**：83 项，其中 **70 项指向同一个默认处理函数 `0x7AF2`**，
  只有 11 个不同入口（`0x7AF2 0x7AFE 0x7B18 0x7B7C 0x7C00 0x7C5E 0x7CB6 0x7D96 0x7E00 0x7E74 0x7EA4`）。
  稀疏表 + 统一默认值，典型的 BLE 事件/消息分派结构。
- **`0xD31C` 跳转表**：30 项、23 个不同地址，从 `0xB882` 递增到 `0xBF52`，
  间隔多为 30–160 B —— 更像 switch-case 的 case 地址表，而不是 30 个独立函数。
- 这 34 个入口**没有一个出现在 290 个 `tjl` 目标里**，说明固件大量使用间接调用；
  只靠静态调用图会漏掉这批代码。

## 5. 硬件寄存器使用（对照 TLSR8258 datasheet）

| 地址 | 含义 | literal 引用 / 涉及函数 |
| --- | --- | --- |
| `0x800740` | `SYS_TIMER0`，16 MHz 系统 tick | 89 次 / 40 个函数 —— 所有延时、超时、软定时 |
| `0x800744` | system timer 区 | 16 次 / 11 个函数 |
| `0x800643` | `IRQMODE`，全局中断使能 | 32 次 / 22 个函数 |
| `0x800640`–`0x642` | 中断掩码 | 见各函数 literal |
| `0x8005xx` | GPIO 配置/输入输出（`0x580`–`0x5A8` 段） | `0x800540`/`0x800548` 各 10 次，5 个函数 |
| `0x800F00` / `0x800F20` | 未查明（疑似 RF/analog/flash 控制） | 8 / 16 次 |
| `0x80000C` / `0x80000D` | 未查明 | 12 / 20 次 |

literal pool 的 1,688 个引用按目标分类：RAM `0x84xxxx` 867 次、IO 寄存器 384 次、
代码/常量 176 次、其它 251 次。**没有任何一次直接指向 `0x40000` 日志区或 `0x76000` 校准区**。

## 6. 新发现（协议文档与静态分析里都没有的）

1. **56 字节无结构常量块 `@0xD2A8–0xD2E0`**：`64 10 b7 1d … 78 e2 0a a0`，51 个不同字节值、
   熵 5.63（代码区 `0xCC00` 为 5.93，**熵本身不能证明是加密材料**）。位置夹在配置常量与函数指针表之间，
   疑似 BLE 安全/随机相关常量，**用途未证实**，不要当成密钥或后门。
2. **两张函数指针表与 34 个间接入口**（§4）。
3. **`0x3000–0x3FFF` 4 KiB 区在整个固件里没有任何代码引用**（0 调用、0 literal），
   比"低熵数据表"更可能是保留/校准扇区。
4. 命令分发与回包构造的确切地址（§3）。
5. `0x800740` 系统 tick 被 40 个函数使用 —— 说明大量逻辑是基于 tick 的软定时，
   与「对时后按 Unix 秒调度、未对时用 1970 起秒数」的观察相容。

## 7. 还不知道的

- 向量表 64 × `0x06C0` 的确切语义；头部 `0x0C` 字段；原厂尾部校验算法。
- `0xD2A8` 无结构常量块、`0x3000` 近全零区的用途。
- 34 个间接入口各自做什么；`0x2EA0` 那个 2,224 条指令的大函数是不是主循环。
- 命令分发 switch 每个 case 对应的命令；`EC/86/88/3C` 及顶层未知命令码未验证
  （`A0/A2/A3/A5/A6` 已于真机确认，见 §3）。
- **定时调度与日志落盘的代码路径**：`0x40000` 没有直接引用，只找到两处 `0x3FF00`
  （`@0xB254`、`@0xB572`）和若干 `tmov #0x40`；怀疑通过扇区号参数化访问，未坐实。
- `0x800Fxx`、`0x80000C/D` 寄存器用途；消杀/UV 具体由哪个 GPIO 驱动。
- 是否存在协议文档之外的隐藏 BLE 命令或调试入口。
- 没有符号表，所有函数只能按地址和引用关系标注，无法自动命名。
