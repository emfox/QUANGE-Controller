# 路线 3：白名单能不能绕，以及「模拟消毒器」到什么程度为止

2026-11-08。回答两个问题：不申请官方白名单能不能把设备伪装成消毒器；如果不能，路线 3 还剩下什么可做。

**结论**：进米家 App 这条路绕不过去，三道门全是云端身份，不是协议格式；但**协议层自测可以完全不依赖小米任何资源**——因为可以自己扮演手机那一端。

---

## 1. 三道门，逐条对证

| 门 | 卡什么 | 官方原文 |
| --- | --- | --- |
| ① App 发现 | Product ID 必须在平台的产品表里，且账号在可见范围 | 「不定义 `PRODUCT_ID` 则默认为 156 小米蓝牙开发板，**此产品为白名单用户可见**（如需使用此 PID 进行功能验证，请申请白名单权限）」 |
| ② 绑定 | 云端按 MAC 下发 token | 「请确认设备是否已上线或者**用户的小米ID是否在设备的白名单中**」「修改 PID 后无法绑定成功，极大可能是**服务器端未上线**」 |
| ③ Mesh 配网 | 证书链 | 「如果是高安全认证或者 mesh 认证，**每个安全芯片/证书链只能绑定唯一一个 PID 和 MAC**，如需更改 PID 或 MAC 请更换安全芯片/证书链」 |

以及：「在模组中烧录固件时…若模组**全片 erase** 将会导致**证书链丢失**，设备配网绑定将无法成功。」

两条信息合起来给出分界线：

| 认证形态 | 门槛 | 能不能自己造 |
| --- | --- | --- |
| 标准型（弱绑定）BLE 直连 | PID + token（token 由云端按 MAC 下发） | token 可以自定，但**云端不认识这个 MAC**，登录必然失败 |
| 高安全认证 / Mesh | 证书链，一芯一证 | **不能**，这是小米签发的，无法生成 |

所以「模拟消毒器」缺的从来不是帧格式，是**云端的一条登记记录**。

## 2. 好消息：这台设备本来就是直连型

现固件是 GATT 私有服务（`1001`/`1002`）、手机和小程序直连，**不是 mesh**。

⟹ 路线 3 应该走 **`0xFE95` 直连分支**，不要改造成 mesh。理由：

- mesh 那一路是证书链硬墙，物理上过不去；
- 直连这一路只差一次云端登记，协议栈本身可以在网上找到完整实现；
- 改造面小得多：现有 `1001` 服务可以原样保留并行跑，出问题还能用小程序控制。

## 3. ⚠️ 更正：L1 广播不能靠静态补丁

之前说「L1 已做完」（`591725f`）**是错的**。把 `0x47D0` 那段反汇编读全之后：

```
0x47D0  r0 = sp + 0x14                      ; 栈上的广播缓冲
0x47D2  r7 = 0xCD00                         ; 模板
0x47D8  tloadm / tstorem ×2                 ; 拷 27 字节进栈
0x47E6  byte[r4+5] → buf[21]
0x47E8  byte[r4+4] → buf[22]
  ...                                        ; 六条 tloadrb/tstorerb，
0x47FC  byte[r4+0] → buf[26]                 ; 把 r4 的 6 字节逆序写进 buf[21..26]
0x47FE  r1 = 27
0x4800  tjl 0x90F8                          ; 设广播数据（长度硬编码 27）
```

模板 `0xCD13` 起的 8 字节是 `07 FF AA AA AA AA AA AA`，其中偏移 **21..26 正好是那 6 个 `AA`**。也就是说：

**那 6 个字节是留给 MAC 的占位，每次广播前都会被真 MAC 覆盖。**

我们上一版把 company / Frame Control / PID 写进这 6 个字节，PID 落在偏移 25、26 —— **上电就被 MAC 的低两字节冲掉**，广播出去的不是 MiBeacon。

而且结构上也没有余量：模板给这一个 AD 元素只留了 8 字节（`07 FF` + 6），而 MiBeacon 的强制字段是 Frame Control(2) + Product ID(2) + Frame Counter(1)，加上 company 至少要 9 字节。

⟹ **广播层必须是代码生成，不能是模板替换。** 对 MiBeacon 而言本来也只能这样：帧计数器要递增，capability 和 object 要按状态填，静态模板永远做不出来。

所以 `tools/mi_patch.py` 已删除，那条「L1 零代码改动」的结论作废。这一条不亏：路线 3 反正要自己写广播，早点发现比烧进去再发现好。

## 4. 「模拟消毒器」能到哪一步

| 层 | 能做到 | 米家 App 认不认 |
| --- | --- | --- |
| 广播 | 生成完全合法的 MiBeacon，PID 填任意值 | **不认**——PID 不在产品表，或账号不在白名单 |
| `0xFE95` + 标准认证 | 完整握手、AES-CCM 加密读写，行为与真设备一致 | **不认**——云端查不到这个 MAC 的 token |
| 在 App 里显示成「消毒器」 | 需要 `sterilizer` 品类下、已登记的 PID + MAC + token | **做不到**，PID 是平台创建产品时分配的 |

第三行是死结，前两行是「协议对了、身份没有」。

## 5. 不申请任何东西，能做到的三件事

### 5.1 协议沙盒（推荐，唯一零依赖）

自己当手机那一端。**token 由我们自己定**，所以不需要云端：

- 设备端：MiBeacon + `0xFE95` + 标准登录，token 编译期写死；
- 主机端：Python + `cryptography`（ECDH P-256、HKDF-SHA256、AES-CCM-128），扮演米家 App；
- 跑通「发现 → 绑定 → 登录 → 加密读写属性」全流程。

验证清单（每条都能独立判定）：

1. 广播能被解析成 MiBeacon，PID / 帧计数器 / capability 正确；
2. 连接后 `0xFE95` 服务与特征表符合规范；
3. ECDH 交换公钥成功，双方算出的共享密钥一致；
4. HKDF 导出的会话密钥一致；
5. 绑定包（device public key + CRC32）加密后对端校验通过；
6. 登录后的属性读写能正确解密；
7. 重连后走登录而不是绑定；
8. 断电重启后绑定信息仍在（flash 持久化正确）。

这套东西的价值在于：**等拿到白名单或自己的 PID，只改 PID 和 token 两个常量，其余一行不动。**

### 5.2 借真模组（零白名单，但身份是通断器）

拆一颗米家蓝牙 Mesh 通断器，模组里的证书链、PID、MAC 都是真的、都在产线系统里登记过。能进米家、能开关、能点动 180 秒。但它显示成「通断器」，**显示不成消毒器**——那是 PID 决定的。

### 5.3 等白名单

个人开发者通道目前「内测名额已满，暂不对外开放」；企业开发者要营业执照。这条不是技术问题。

## 6. 建议的顺序

1. **沙盒**（本周可做完大半）：把协议栈和属性映射在本地跑通，不需要任何小米资源；
2. 沙盒跑通后，业务层按 `sterilizer` 的属性集定型（`on` / `mode` / `status` / `target-time` / `working-time` / `left-time` / `fault`），见 [同类设备调查](mi-home-migration.zh-CN.md) §3；
3. 再决定身份怎么来：申请自己的 PID，还是先用 156 + 白名单验证。

沙盒这一步不依赖前两步的决定，做了不浪费。

## 7. 沙盒要在 TC32 上实现的东西（按工作量排）

| # | 内容 | 参考 |
| --- | --- | --- |
| 1 | MiBeacon 发送（帧计数器、capability、object） | `tools/mibeacon.py` 是这一层的 Python 参考实现，自检通过 |
| 2 | `0xFE95` 服务与特征 | 按 `mible_server_miservice_init` 的语义对齐，不自己发明 UUID |
| 3 | 标准登录：ECDH P-256 + HKDF-SHA256 + AES-CCM-128 | 固件里现在只有 TRNG，**AES/ECC 全要新写**，这是最大一块 |
| 4 | miot-spec 属性映射 | 见同类设备调查 §5 |
| 5 | 与现有 `1001`/`1002` 私有服务并行 | 两套 GATT 可以共存 |

第 3 项是真正的工作量：TC32 上要补 AES-128、CCM 模式、P-256 点乘、SHA-256、HKDF。其中只有 TRNG 是现成的。

## 8. 待确认

- `r4` 指向的 6 字节是否就是 BLE 地址（逆序写入 + 长度 6，指向性很强，但没在真机上读内存核对）；
- 广播长度常量 `27` 是否只在这一处（`0x47FE`）设定，还有没有别的地方重设；
- 若将来要在真机上验证 L1，用 nRF Connect 抓一次 scan response 即可判定，不需要改代码。
