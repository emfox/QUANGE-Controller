# 接入米家：可行性与边界

本机原厂只支持微信小程序 + 私有 BLE 协议，**从未接入米家**。本文回答三个问题：
接进去在协议上要做多少、品类上能不能对上、身份那一关要什么条件。

**结论**：协议层可以自己做，业务语义与米家 `sterilizer` 品类几乎一一对应；
真正的门槛是**云端的一条 (PID, MAC) 登记记录**，与帧格式无关。

> 状态：**暂停**（2026-11-08）。代码与文档结论保留在此，等身份问题有解再继续。

## 1. 本机是什么

**全格智能杀菌牙刷杯架，型号 WY020702**（品牌 QUANGE，上海莱枫生活用品有限公司）。

| 固件里的证据 | 实物 |
| --- | --- |
| 广播名 `QUANGE-WY020702`（`0xCCEB`） | 品牌 QUANGE + 型号 WY020702 |
| 序列号 `LFWY020702/…`（flash `0x43000`） | 同上，`LFWY` + 型号 |
| 型号串 `Hi-YM01-12DC2110000`（`0x2F8C`） | 内部料号 |
| 电量查询（命令 `03`，RAM `0x8435A0`） | 电池供电（该型号是电池版） |
| 4 槽本地定时 | 说明书写「每 6 小时自动杀菌一次」＝一天 4 次 |
| 180 秒固定档（`0x6538`，`+0x35 != 0`） | UVC 杀菌时长 |
| 长按标志 `+0xB` | 说明书写「长按切换开关、双击强制消杀」 |

评测里提到的「智能雷达感应，1.5 m 内无人时才工作」，在固件里对应哪个 GPIO 尚未对出。

**它的"适配米家"是尺寸适配，不是协议接入。** 评测原文是「适配米家系列全型号的电动牙刷」，
说的是挂孔放得下米家的电动牙刷。同类产品里这种情况是常态：

| 类型 | 判据 | 例子 |
| --- | --- | --- |
| 真接入 | 米家 App 里能搜到、能绑定、能控制 | FIVE、紫物、小米自有 |
| 只有说法 | "适配米家"、"在米家有品卖"、"生态链出品"，实际不联网 | 本机 WY020702、Oclean S1 |
| 另一套生态 | 自己的 App/小程序 | 大量白牌 |

Oclean S1 是最典型的一个：它在有品销售、由华米系品牌出品，但**没有 PID、没有 model、
没有任何无线连接项**。官方 FAQ 的操作全在本体上——挂墙每 6 小时自动消毒 2 分钟、
拉绳一次进入 5 分钟档、取下自动关机；规格只有 1000 mAh 电池、Type-C、UVC-LED、
蓝色指示灯和霍尔开关。它的"6 小时一次"与本机 4 槽定时的思路完全一致，
说明**这个品类的默认形态本来就不联网**。

## 2. 米家品类：`sterilizer` 与线上型号

米家有正式的设备类型 `urn:miot-spec-v2:device:sterilizer:0000A04F`。查到的线上型号：

| 品类 | 型号 | 产品 ID | 协议 | 厂商 | 发布 |
| --- | --- | --- | --- | --- | --- |
| `sterilizer` | `uvfive.steriliser.maine`（FIVE 智能刀筷杀菌架） | **6638** | **Wi-Fi** | FIVE | 2021-11 |
| `sterilizer` | `xiaomi.steriliser.uvs01`（米家智能消毒机 25L） | **25643** | **Wi-Fi** | 小米 | 2025-10 |
| `germicidal-lamp` | `uvfive.s_lamp.slmap2`（FIVE 智能消毒杀菌灯） | **68812** | **MiIO/Wi-Fi** | FIVE | 2020-03 |
| `germicidal-lamp` | `ziwooo.s_lamp.uvc`（紫物智能消毒杀菌灯 Pro） | **70276** | **MiIO/Wi-Fi** | 紫物（上海） | 2020-09 |
| `foot-bath` | `xiaomi.foot_bath.mizs1`（米家**杀菌**足浴器） | **13223** | **BLE Mesh** | 小米 | — |

四台 Wi-Fi/MiIO 设备都标注「需要网关：不需要」——它们连路由器。

`uvfive.steriliser.suger` 只有 spec、没有产品页（`/p/` 为 404，只挂 `v2debug` 标记），
属**未发布模板**，没有 PID。但它的服务树正是我们要的那套：

`fault` · `mode`(15/30/60 分钟) · `on` · `status`(Idle/Busy) · `target-time`(15–60, 步长 15)
· `working-time` · `left-time`，另加 `alarm`、`physical-controls-locked`、`door`。

**关键事实：这个品类没有任何 BLE 型号。** 而 PID 不只标品类，它决定**配网通道**——
米家读到 Wi-Fi 设备的 PID 就去走 Wi-Fi 配网，BLE 设备连"发现"阶段的表现都不对。
所以"借一个消毒器的 PID 给 BLE 设备用"在数据层面是空集。

唯一带 BLE 的是浴足器 `13223`，但品类是足浴盆，且走 mesh。

## 3. 属性映射

### 3.1 走 `sterilizer`（语义最贴，但该品类只有 Wi-Fi）

| 我们的命令 | 现在的行为 | 米家对应 |
| --- | --- | --- |
| `04` | 立即开 / 关 + 设时长 | `on`(bool) + `target-time` |
| `02` | 状态查询 + 对时 | `status` + `working-time` + `left-time` |
| 档位（`+0x60`） | 档位时长表 | `mode` |
| `0x64D0` 收尾 | 完成 / 中止 | `fault` = 1 完成 / 2 中止 |
| `03` | 电量百分比 | 标准 `battery-level` service |
| `07` / `08` | 4 槽本地定时表 | 不需要——米家由网关/云端调度 |
| `05` / `06` | 200 条日志（栈式） | 无对应；可保留为私有 service，或丢弃 |
| `09` / `A2` / `A3` / `A5` / `A4` | 序列号 / MAC / 版本 | 由米家认证与 OTA 流程接管 |
| `A0` | 恢复出厂 | 米家 App 的「删除设备 / 重置」 |

业务语义是超集，能对上；工程实现是另一套栈。

### 3.2 走开关 / 通断器（BLE 型号大量存在）

开关品类的 PID 是真实可用的 BLE 设备，语义也够：

| 型号 | 产品 ID | 协议 | 厂商 | 发布 |
| --- | --- | --- | --- | --- |
| `wainft.switch.sw0a02`（XG 蓝牙 Mesh 通断器） | **4380** | BLE Mesh | 馨光 | 2021-03 |
| `zxlink.switch.zxltdq`（智相连 Mesh2.0 通断器） | **35553** | BLE Mesh | 智相连 | 2026-04 |
| `bean.switch.bl04`（四键单火开关 V2-Mesh 版） | **14918** | BLE Mesh | 翼数 | 2023-08 |

`wainft.switch.sw0a02` 的 spec 几乎就是这台设备：

| spec 属性 | 范围 | 对应我们的 |
| --- | --- | --- |
| `switch.on` | bool | 命令 `04` 立即开关 |
| `function.jog` | 0 关 / 1 开 | 点动模式 |
| `function.delaytime` | **1–3600 秒** | 180 秒固定档正好落在范围内 |
| `function.default` | ON / OFF / Memory | 上电默认状态 |
| `function.inteligent-switch` | 0 / 1 | 灵动（掉电翻转） |
| `function.device-reset` | 写 1 | 恢复出厂 |
| `remote.*` | 8 个遥控器槽 | 无对应 |

`zxlink.switch.zxltdq` 的官方 FAQ 里还有一句：「在米家 App 中，将设备从网关模式切换至
**蓝牙直连模式**」——通断器这一类本来就存在不经网关、手机直连的用法。

代价是显示成"通断器"而不是"消毒器"。PID 决定品类，这一点改不了。

## 4. 准入边界：三道门

| 门 | 卡什么 | 官方原文 |
| --- | --- | --- |
| ① App 发现 | PID 必须在平台产品表里，且账号在可见范围 | 「不定义 `PRODUCT_ID` 则默认为 156 小米蓝牙开发板，**此产品为白名单用户可见**」 |
| ② 绑定 | 云端按 MAC 下发 token | 「请确认设备是否已上线或者**用户的小米ID是否在设备的白名单中**」「修改 PID 后无法绑定成功，极大可能是**服务器端未上线**」 |
| ③ Mesh 配网 | 证书链 | 「如果是高安全认证或者 mesh 认证，**每个安全芯片/证书链只能绑定唯一一个 PID 和 MAC**，如需更改请更换安全芯片/证书链」 |

以及：「在模组中烧录固件时…若模组**全片 erase** 将会导致**证书链丢失**，设备配网绑定将无法成功。」

分界线在这里：

| 认证形态 | 门槛 | 能不能自己造 |
| --- | --- | --- |
| 标准型 BLE 直连 | PID + token（token 由云端按 MAC 下发） | token 可自定，但**云端不认识这个 MAC**，登录必然失败 |
| 高安全 / Mesh | 证书链，一芯一证 | **不能**，小米签发，无法生成 |

**本机是直连型**（私有 GATT `1001`/`1002`，手机直连，不是 mesh），所以方向只有一条：
`0xFE95` 直连分支。mesh 那一路是证书链硬墙，物理上过不去；直连只差一次云端登记，
而且现有 `1001` 可以原样保留并行跑，出问题还能用小程序控制。

## 5. 申请通道

**企业组**：《成为开发者》页原话「目前，小米 IoT 平台仅面向企业开发者开放」「仅面向中国大陆地区
注册成立的公司开放」，要营业执照、法人、地址。有一个细节值得问清楚：
「（**不包含个体工商户**）」只出现在《服务商准入、考核、退出规则》里，
**企业开发者的注册文档里没有这句排除**，所以个体工商户能否注册企业组，官方没明文封死。

**个人开发者通道**真实存在，于 2023-12-01 开放内测（首批 1000 名，送 1 片模组开发板，
5 个工作日审核），当前标注「内测名额已满，暂不对外开放」。它给的权限恰好够用：

| 权限 | 对我们的意义 |
| --- | --- |
| 不用创建产品，用预置模板 | 不需要自己申请 PID |
| 模板含灯、开关、插座、**通断器/继电器**、窗帘电机 | 通断器正是要的品类 |
| 不能改模板功能 | 够用：`on` + 点动 + 延时都在 |
| 不能上线、不能分享 | 本来就只给自己用 |
| **可以用自己的账号控制设备** | 这就是目标 |
| 固件刷设备 + 扩展程序刷**调试版米家 App** | ← 关键 |

最后一行是重点：个人开发者用的是**调试版米家 App**，不查云端可见性。所以第①道门和
第②道门的一半在这条路上不存在，也不用上线审核、不用寄硬件评审。它唯一不解决的是
Mesh 证书链——只能做标准 BLE 直连，与已定的方向一致。

现在能做的：登录 iot.mi.com 看「申请内测个人开发者」入口的实时状态（文档里的"名额已满"
可能是旧说法），并提工单问两件事——内测何时再开、有没有候补；个体工商户执照能否注册企业组。

## 6. 三条落地路线

| 路线 | 做法 | 固件改动 | 保留 | 代价 |
| --- | --- | --- | --- | --- |
| **桥接** | 原板不动，外挂米家通断器驱动消杀回路 | **0 行** | 米家只有开/关 + 点动 | 需要接线；两套电源；原机小程序仍可用 |
| **换控制板** | 拆原 MCU，米家模组直驱负载 | **0 行** | 米家全功能，丢日志与本地定时 | 不可逆 |
| **自写固件** | TLSR8258 上跑小米 SDK，实现 `sterilizer` model | 业务层重写 | 全部可控 | 需 PID + 认证库 |

三条都不需要伪造别人的 PID：前两条用的是已认证的正规模组，第三条走官方注册。

可当载体的米家硬件：模组 **MHCB07P**（Realtek RTL8762CGL，官方报价 5.99 元，
**不对个人销售**）与 **MHCB12S**（Mesh 2.0）。模组背面 8 pin 扩展板丝印
`GND / 3V3 / W / Y / R / G / B / AC`，`W` 是单路输出。出厂固件自带
**点动延时 1–7199 秒**——180 秒固定档正好落在里面。米家 Mesh 的定时与倒计时由
网关/云端调度，不依赖设备本地定时表，所以迁移过去后 4 槽表和软定时器可以整个丢掉。

## 7. 广播层只能代码生成

扫描响应模板 `0xCD00` 尾部是 `07 FF AA AA AA AA AA AA`。把它当 MiBeacon 的槽位用**不成立**：

```
0x47D0  r0 = sp + 0x14                      ; 栈上的广播缓冲
0x47D2  r7 = 0xCD00                         ; 模板
0x47D8  tloadm / tstorem ×2                 ; 拷 27 字节进栈
0x47E6  byte[r4+5] → buf[21]
  ...                                        ; 六条 tloadrb/tstorerb
0x47FC  byte[r4+0] → buf[26]                 ; r4 的 6 字节逆序写进 buf[21..26]
0x47FE  r1 = 27                             ; 长度硬编码
0x4800  tjl 0x90F8                          ; 设广播数据
```

偏移 `21..26` 正好是那 6 个 `AA`，**每次广播前都被真 MAC 覆盖**；而且这一个 AD 元素只留了
8 字节，MiBeacon 的强制字段（company 2 + Frame Control 2 + PID 2 + Frame Counter 1）要 9 字节。

⟹ 广播必须是代码生成。对 MiBeacon 本来也只能这样：帧计数器要递增，capability 与 object
要按状态填，静态模板做不出来。

`tools/mibeacon.py` 是这一层的编解码参考实现（含自检，向量取自真机 LYWSD03MMC 广播），
可以校验任何 MiBeacon 帧的合法性。

## 8. 协议沙盒：不依赖小米任何资源

自己扮演手机那一端，**token 自定**，完全不碰云端：

- 设备端：MiBeacon + `0xFE95` + 标准登录，token 编译期写死；
- 主机端：Python + `cryptography`（ECDH P-256、HKDF-SHA256、AES-CCM-128）；
- 跑通「发现 → 绑定 → 登录 → 加密读写属性」。

验证清单（每条独立可判）：

1. 广播能被解析成 MiBeacon，PID / 帧计数器 / capability 正确；
2. `0xFE95` 服务与特征表符合规范；
3. ECDH 交换公钥成功，双方共享密钥一致；
4. HKDF 导出的会话密钥一致；
5. 绑定包（device public key + CRC32）加密后对端校验通过；
6. 登录后的属性读写能正确解密；
7. 重连后走登录而不是绑定；
8. 断电重启后绑定信息仍在。

价值在于：**等拿到白名单或自己的 PID，只改 PID 和 token 两个常量，其余不动。**

在 TC32 上要实现的东西，按工作量排：

| # | 内容 | 参考 |
| --- | --- | --- |
| 1 | MiBeacon 发送（帧计数器、capability、object） | `tools/mibeacon.py` |
| 2 | `0xFE95` 服务与特征 | 按 `mible_server_miservice_init` 的语义对齐，不自己发明 UUID |
| 3 | 标准登录：ECDH P-256 + HKDF-SHA256 + AES-CCM-128 | 固件里只有 TRNG，**AES/ECC/SHA 全要新写** |
| 4 | miot-spec 属性映射 | §3 |
| 5 | 与现有 `1001`/`1002` 并行 | 两套 GATT 可以共存 |

第 3 项是真正的工作量：TC32 上要补 AES-128、CCM、P-256 点乘、SHA-256、HKDF。

## 9. 待确认

- `r4` 指向的 6 字节是否就是 BLE 地址（逆序写入 + 长度 6，指向性很强，未在真机读内存核对）；
- 广播长度常量 `27` 是否只由 `0x47FE` 设定，还有没有别处重设；
- 若要在真机验证广播，用 nRF Connect 抓一次 scan response 即可判定，不需要改代码。
