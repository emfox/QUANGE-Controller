> **关于芯片型号：PnP ID 查不出来**
>

> 但**即便读对了，`0x8266` 也不能用来判断芯片型号**。源码级核查发现这是 Telink BLE SDK
> 参考设计里写死的数组，所有用默认配置的 Telink 设备读出来一模一样：
>
> ```c

> ```
>
> 所以 PID 字段反映的是**编译进固件的 SDK 默认值**，不是实际封装。
> **芯片型号在 BLE 层没有任何可观测线索，只能拆机看丝印。**

> **主体辨析（2026-11-08 核正）**：「全格 QUANGE」是**上海莱枫生活用品有限公司**的自有品牌，
> 该公司也是本机包装 / 说明书上的产品责任主体（统一社会信用代码 `91310120MA1HQ17M3W`，
> 官网 `sh-lifefun.com`）。「**莱枫智能生活**」只是**小程序名称，不是公司名**；
> 早期笔记里的「杭州莱枫智能」**查无此实体**。品牌方 ≠ 模组 / 固件 / 代工方仍成立
> （Telink 模组、OUI `1C:45:C2` 属惠州三信、广东中山代工），
> 但不能据此推定存在一家「杭州」方案商。依据见 [README](../README.md)「设备信息」。
>
> **关于 `kHID`**：它是蓝牙模块的**出厂默认广播名**，不是这台设备的品牌名。
> 成因是上游厂商（**上海莱枫生活用品有限公司**，官网 `sh-lifefun.com`，「全格」是它的自有品牌）
> 直接复用了 HID 产品线（自拍器/键盘）的固件配置，改造成杀菌盒时**没有改广播配置**。原厂 App 的「改设备名」走云端接口、从不下发到设备
> （见 miniprogram 文档 §3.7），所以这个名字只能是产线烧录时写死的。
>
> **广播里的 `0x1812` 是同一块残留，不是能力。** 实测导出完整 GATT 树，
> 里面**没有 HID 服务**（只有 GAP/GATT/DIS/电池 + `000000FB` + Telink OTA）。
> 也就是说设备在广播里声明了一个自己不提供的服务。
>
> 由此得出一条实践结论：**广播名和 `0x1812` 出自同一处配置，都不能当作稳定标识**。
> 名字改写只走已下线的云端接口、设备侧没有写入路径，因此「改名后 `0x1812` 是否消失」
> 无法实测，已主动关闭（见 §9）。
> **只有 MAC 是可靠的**。
>
> 反过来，**原厂小程序只认 `QUANGE-WY020702`**（`conble.js` 里写死两处），
> 所以设备处于 `kHID` 状态时原厂 App 会搜不到 —— 这是原厂代码的问题，不是设备故障。
> 我们的 `phone.html` / `set_timer.py` 认三个前缀 + 服务兜底，两种状态下都能连。
>
> **切换的触发条件已实测（2026-11-08，USB 常供电）**：两轮各 60 s 原始广播抓取，
> `kHID` 都只出现在**该轮扫描的第一个包**（A 轮 1/121、B 轮 1/98），之后全部是
> `QUANGE-WY020702`；RSSI、服务 UUID、Manufacturer Data 全程一字未变。中间连接一次再断开，
> 重新扫描时又重现同样模式。所以**不是「两种名字来回轮换」**，而是启动瞬间的默认名 +
> 随即固定。`kHID` 可能来自扫描器启动时回吐的缓存广播，也可能是固件首包，**机制未定**，
> 但行为规律已确定。实践上：别在扫描开始第一秒就按名字下结论，或干脆按 MAC 连。

> **别混淆两件事**：这里说的"无加密"指的是**设备之间的 BLE 帧**。
> 小程序包本身是**有加密**的（`V1MMWX` 容器，去掉 6 字节头后整段 XOR 0x30），
> 那是发布方的包壳保护，跟设备协议没有关系。
> 换句话说：**包要解密，协议不用。**

> 广播里**不含私有服务 UUID**（`0x00FB` 只在连接后才出现），所以无法按业务服务过滤。
> 能用的只有名字和那条残留的 `0x1812` 声明 —— 两者都会随配置变化，见上方说明。

### GATT 结构

| Service | Characteristic | 属性 | 用途 |
| --- | --- | --- | --- |
| `00001800` | `2A00` / `2A01` / `2A04` | read | 标准 GAP |
| `00001801` | `2A05` | indicate | 标准 GATT |
| `0000180A` | `2A50` | read | PnP ID |
| `0000180F` | `2A19` | read / notify | 电量 |
| `000000FB` | **`00001001-0000-1000-8000-00805F9B34FB`** | read / **write-without-response** / notify | **指令下发** |
| `000000FB` | **`00001002-0000-1000-8000-00805F9B34FB`** | read / notify | **设备回包** |
| `00010203-0405-0607-0809-0A0B0C0D1912` | `...0A0B0C0D2B12` | read / write-without-response | OTA 升级专用 |

`1001` 的 CCCD 受权限保护（订阅会返回 `Write Not Permitted`），但**写入不受限制**；
回包走 `1002`，可以正常订阅。

## 2. 帧总则

- 方向：主机 → 设备，帧首字节 `0xDB`；设备 → 主机，帧首字节 `0xBD`
- 字节序：多字节字段一律**大端**
- 数值字段一律以**数值本身**表示（不做 BCD 转换）：15 点 = `0x0F`，不是 `0x15`

### 帧结构

```
DB | CMD | SUB | [LEN] | [DATA...]
```

`CMD` + `SUB` 组成功能码，例如 `DB 02 04` 是开关类，`DB 08 08` 是设定时类。

## 3. 指令表

| 功能 | 帧 | 回包 |
| --- | --- | --- |
| 立即开启（消杀） | `DB 02 04 01` | `BD 0B 02` |
| 关闭 | `DB 02 04 00` | `BD 0B 02` |
| 查询状态 | `DB 04 02` + 4B unix 秒 | 设计上为 `BD 0E 02` 等（§5.1）；**本机固件实测不回包**，见 §9 |
| **查询定时列表** | **`DB 01 07`** | `BD 0D 07` |
| 查询消杀日志 | `DB 01 05` | `BD 08 05` |
| 设置定时（整表覆盖） | `DB 08 08` + `Count` + `[HH MM 0D] × Count` | `BD 0D 08`，**但可能不回**；成败必须 `DB 01 07` 回读 |
| 删除定时 | `DB 00 08` + `Count` + `[HH MM 0D] × Count` | — |
| 版本 | `DB 01 A4` | `BD 06 A2` + 6 字节 ASCII 版本串（实测 `"000014"`，见 §8.2） |
| 设备复位 | `DB 01 A0` | — |
| 日志确认 | `DB 06 06 01` + 4B 时间戳 | — |
| OTA 分包 | `01 FF` / `02 FF ...` | — |

> `DB 01 07` 单独发送时设备**不回复**。必须先走一遍完整时序
> `DB 04 02` → `DB 01 05` → `DB 01 07`，才会收到 `BD 0D 07`。
> 这是本协议最反直觉的一点，实测踩过坑。

### 3.1 开关

```
DB 02 04 01     开启（UVC 工作约 3 分钟，指示灯呼吸）
DB 02 04 00     关闭
```

### 3.2 查询状态

```
DB 04 02 | TS(4B 大端, unix 秒)
```

时间戳给设备校准时钟，同时是后续 `DB 01 07` / `DB 01 A4` 的前置条件。
**每次连接后先发这一帧。**

> ⚠️ **必须先订阅 `1002` 再发这一帧。** 2026-11-07 实测：
>
> | 条件 | 结果 |
> | --- | --- |
> | 未订阅 `1002` 时发送 | **收不到**，且**不缓存** —— 之后补订阅也收不到 |
> | 已订阅 `1002` 时发送 | 立刻回 `BD 0E 02 ...` |
> | 订阅 `2A19`（电池）后再发 | 同样正常回包，`2A19` 与否无关 |
>
> 过去记录的"多次实测全部无回包"就是这个原因：**发早了，回包被丢弃**。
> `set_timer.py` 与 `phone.html` 都是先订阅再发，因此不受影响；
> 自己写客户端时别把顺序搞反。
>
> **这一帧的时间戳就是设备时钟本身**（2026-11-08 实测）：把它设成 `0x00000100`，
> 状态回包 `26..34` 原样回显 `00000100`，`next run` 随之变成 `0x00006270`
> —— 即 UTC+8 本地 08:04 之后的下一个定时点 15:00（UTC 07:00 = 25200 s）。
> 说明设备**按 UTC+8 本地 HH:MM 判断定时**；发真实 unix 秒即可，无需换算。
>
> **消杀期间状态回包正常**（6/6 次）：`BD0E02 01 ...` 持续返回，`12..16` 从
> `001E`(30 s) 递增到 `00A0`(160 s)，结束归零。早期「开机消杀期间不回包」的
> 单次观察不成立，更可能是刚上电时尚未就绪。

### 3.3 设置定时

```
DB 08 08 | Count(1B) | [HH(1B) MM(1B) 0D(1B)] × Count
```

- `Count`：本次写入后的**总条数**，设备按整表覆盖处理
- `HH`：小时，0–23
- `MM`：分钟，0–59
- `0D`：消杀时长，**1 字节分钟数**。固件**不校验范围** —— 2026-11-07 实测
  `0x00` / `0x07` / `0x0F` 都被原样接受并写进回包（见 §8.4）。小程序只允许
  3 / 4 / 5 / 6 分钟，是**纯前端规则**；源码里的 `f"0{d}"` 拼串让个位数看起来像
  「`0` + 数字」，但那不是协议里的固定前缀，只是十六进制的高位。

示例：

| 需求 | 帧 |
| --- | --- |
| 每天 03:00，5 分钟 | `DB 08 08 01 03 00 05` |
| 每天 02:00，3 分钟 | `DB 08 08 01 02 00 03` |
| 03:00/5min + 15:30/4min | `DB 08 08 02 03 00 05 0F 1E 04` |

**多条定时已实测可用**：写入两条后，设备回 `BD0D08 030005 0F1E04 FF FF FF FF FF FF 00`，
`DB 01 07` 回读得到同样的两条。

**「4 条」是固件硬限制（实测）**：小程序 `problem` 页的 FAQ 写着"最多设置四条消杀,最少一条"，
而前端代码里**没有硬编码**这个数字 —— 但固件认。实测发 5 条过去：

```
发送  DB 08 08 05  02 00 06  08 00 03  0C 00 03  12 00 03  16 00 03
回包  BD 0D 08     02 00 06  08 00 03  0C 00 03  12 00 03  00
```

第 5 条（22:00）**被静默丢弃**，既没有错误码也没有拒绝回包。原因在载荷结构上：
`BD0D07` / `BD0D08` 的载荷是**恰好 4 个槽位**，满了就没有位置了（见 §4）。

**空槽与尾字节**：`BD0D07` / `BD0D08` 的载荷是**固定 4 个槽位**（每槽 3 字节，空槽 `FF FF FF`），
末尾还有 1 个字节。**2026-11-08 受控实验已定案**：把对时帧时间戳的第 3 字节依次改成
`4D` / `4E` / `4F`，`BD0D07` 末字节就精确跟着变成 `4D` / `4E` / `4F`；同一偏移重复发
则回到 `00`（`BD0D08` 恒为 `00`）。所以它是**设备内部时钟派生的易变字段**
（变化时带上时钟字节），不是校验和、不是电量、与定时表内容无关。
**解析时跳过 `FF` 槽、忽略末字节即可**，不要试图解读它。

> 因为语义是整表覆盖，**不需要先读出当前列表**，直接写目标列表即可。

### 3.4 删除定时

```
DB 00 08 | 剩余条数(1B) | [要保留的项] × 剩余条数
```

小程序源码里的拼接是 `"DB00080" + 剩余条数 + 保留项`。注意 `"DB00080"` 是 **7 个字符**，
末尾的 `0` 会和条数拼成同一个字节，所以落到线路上就是：

| 剩余条数 | 实际帧 | 说明 |
| --- | --- | --- |
| 1 | `DB 00 08 01 03 00 05` | 第四字节 = `01` |
| 2 | `DB 00 08 02 03 00 05 0F 1E 04` | 第四字节 = `02` |
| 0 | `DB 00 08 00` | 清空整个定时表 |

**第四字节是剩余条数**（与新增/修改帧的 `DB 08 08 | 总条数` 语义一致），
只带**要保留**的项，不要带要删的项。

> 源码里这个数字叫 `listLen`，值来自 `t.len - 1`（编辑页传入的现有总条数减 1），
> 删掉一项后正好等于「剩余条数」。
> 因为上限只有 4 条，`0N` 看起来像 BCD，但它是普通十六进制整数，直接按数值写即可。

**实测（2026-11-07，见 §8.4）**：删除帧确实生效，此前只有源码推断。

| 发送 | 回包 | 结论 |
| --- | --- | --- |
| `DB 00 08 01 02 00 03` | `BD0D08 020003 FFFFFFFFFFFFFFFFFF 00` | 定时表只剩 1 条 |
| `DB 00 08 00` | 本窗口 0 帧，下一窗口收到全 `FF` 空表 | 清空生效，但回包可能延迟 |

和 `DB 08 08` 一样：**清空帧不保证当场有回包，成败一律回读确认**。

## 4. 定时项编码细节

设备内部把定时表存成定长槽位，每槽 3 字节，**固定 4 槽**。回包中空槽以 `FF FF FF` 填充。

例：只设一条 03:00/5min 时，`BD0D08` 回包为

```
BD 0D 08 | 03 00 05 | FF FF FF FF FF FF FF FF FF | 0C
                        └── 3 个空槽（共 9 字节）
```

已实测 **2 条**同时写入并回读一致。槽位固定 4 个：**写入 5 条时第 5 条被静默丢弃**
（实测，见 §3.3），所以 4 条是固件上限，不是前端约定。

## 5. 回包解析

回包一律 `BD` 开头。**命令字并不固定**，实测出现过 `BD0B02` / `BD0D08` / `BD0E02` 等多种。

判定方式：**取前 6 个 hex 字符（3 字节）作为命令字，精确匹配**。
小程序源码就是这么做的 —— `buf2hex(value).substring(0,6)` 然后一串 `else if("bd0b02"==a)`。
`phone.html` 和 `set_timer.py` 也用同一套规则。

```
前缀（hex 0..6）        含义
BD 0B 02 / BD 0E 02 /
BD 11 02 / BD 00 02 /
BD 02 02                状态类（见 5.1）
BD 0D 07                定时列表回读（见 5.2）
BD 0D 08                定时保存成功（见 5.2）
BD 08 05 / BD 08 06     消杀日志（见 5.3）
BD 06 A2                固件版本（也用于触发 OTA 检查，见 miniprogram 文档 §5.1）
BD 05 A1                低电量告警
```

> 别用「第 4 字节是不是 `0x00/0x01`」来判类型 —— `BD0B02` 的第 4 字节是 `0x00`、
> `BD0D07` 是 `0x07`，这个规则会把 `BD0B02` 当成状态、`BD0E02` 当成别的。
> 老老实实枚举命令字即可。

### 5.1 状态类（`BD0B02` / `BD0E02` / `BD1102` / `BD0002` / `BD0202`）

下标均指**十六进制字符串**的下标（1 hex char = 4 bit，2 个 hex = 1 字节）。
五个命令字共用同一套字段布局。

| hex 下标 | 长度 | 含义 |
| --- | --- | --- |
| `0..6` | 6 | 命令字 |
| `6..8` | 2 | 状态：`01` 正在消杀 / `00` 待机 |
| `8..12` | 4 | 计数器 A（消杀开始瞬间等于本次总时长，实测 `00B4` = 180 s） |
| `12..16` | 4 | 计数器 B（消杀中递增，实测从 `0000` 起） |
| `16..18` | 2 | 电量百分比（hex，`64` = 100%） |
| `18..26` | 8 | **下次杀菌 unix 时间戳**（仅待机时有） |
| `26..34` | 8 | 当前 unix 时间戳（仅待机样本中出现过） |

消杀中的剩余秒数 = `sub(8,12) - sub(12,16)`（实测 `B4 - 0 = 180 s`，与 3 分钟默认时长吻合）。

> **关于 `8..12` / `12..16`（2026-11-08 实测确证）**：这两个字段不是时间戳，
> 而是**本次消杀的总秒数 / 已过秒数**。一次 180 s 真机消杀中连续采样：
>
> | 采样点 | `8..12` | `12..16` | 状态 |
> | --- | --- | --- | --- |
> | +33 s | `00B4` (180) | `001E` (30) | `01` 消杀中 |
> | +65 s | `00B4` | `003E` (62) | `01` |
> | +98 s | `00B4` | `005F` (95) | `01` |
> | +130 s | `00B4` | `007F` (127) | `01` |
> | +163 s | `00B4` | `00A0` (160) | `01` |
> | +196 s | `00B4` | `0000` | `00` 待机，归零 |
>
> 剩余秒数 = `sub(8,12) - sub(12,16)`。做进度显示够用，**别当时间戳用**。

> **为什么不能无脑读 `18..26`：**
>
> 只有**待机**回包（状态 `00`）才有 `18..26` 这段下次杀菌时间戳。
> 状态为 `01`（消杀中）时，实际回包缺这段，硬读 `sub(18,26)` 会拿到
> `0005EEC0` 之类的值，换算出来是 1970 年。
>
> 正确做法：**先看 `6..8` 状态字节，再决定要不要读 `18..26`**；
> 或者读完做一次合理性校验（`> 1600000000`，即 2020-09 之后）。
> `phone.html` 和 `set_timer.py` 都是这么做的。
>
> 注意：本节两个样本是从早期记录里转抄的，转抄时字节分组做过简化，
> **不能当成完整帧长度来用**。判断字段位置请以下标表为准，不要去数样本的字节数。

实测样本（立即开启，状态 `01`）：

```
BD 0B 02 | 01 | 00 B4 | 00 00 | 64 | 00 05 | EE C0 | 00
```

| 片段 | 值 | 含义 |
| --- | --- | --- |
| `BD 0B 02` | 命令字 | 开关类回包 |
| `01` | 状态 | 正在消杀 |
| `00 B4` | 计数器 A | `0x00B4` = 180 s，即本次总时长 |
| `00 00` | 计数器 B | 已过 0 s |
| `64` | 电量 | `0x64` = 100% |
| `00 05 EE C0 00` | 未明 | 语义未确证；`0005EEC0` 不是合理的时间戳，**别读** |

实测样本（待机，已设定 03:00）：

```
BD 0E 02 | 00 | 00 B4 | 00 00 | 64 | 6A DA 5D 30 | 6A D9 F8 82
```

| 片段 | 值 | 含义 |
| --- | --- | --- |
| `BD 0E 02` | 命令字 | 状态类回包 |
| `00` | 状态 | 待机 |
| `00 B4` | 计数器 A | 180 s |
| `00 00` | 计数器 B | 0 s |
| `64` | 电量 | 100% |
| `6A DA 5D 30` | 下次杀菌 | unix 秒 → **2026-10-23 03:00:00** |
| `6A D9 F8 82` | 当前时间 | unix 秒 → **2026-10-22 19:50:26**（比下次杀菌早 7.2 小时） |

### 5.2 定时列表（`BD0D07` / `BD0D08`）

`BD0D07` 是查询结果，`BD0D08` 是保存成功。载荷为定长槽位表，每槽 3 字节，空槽 `FF FF FF`。

### 5.3 日志（`BD0805` / `BD0806`）

| hex 下标 | 含义 |
| --- | --- |
| `6..14` | 开始时间戳（8 hex，unix 秒） |
| `14..18` | 持续时长（秒） |
| `18..20` | 触发类型：`0` 定时 / `1` 非定时（手动按键、**上电自动消杀**，见 §8.4） |
| `20..22` | 记录类型：`00` 开始 / `01` 结束（45 条里 44 条 `01`，最老一条 `00`） |

实测样本：

```
BD 08 05 6A D9 F7 9A 00 B4 01 01
         ↑开始时间戳  ↑180s  ↑类型1 ↑结束
```

**这是一条"流"：设备逐条推送，必须回一次确认才会给下一条。**

流程：

```
发 DB 01 05
  → 收 BD0805（第 1 条，只有首帧用这个命令字）
  → 回 DB 06 06 01 + 该条的开始时间戳（4 字节）
  → 收 BD0806（后续每条都是这个命令字）
  → 回 DB 06 06 01 + 时间戳
  → ……
  → 收 BD0806 FFFFFFFF FFFFFF 00，表示到达缓冲区末尾

（2026-11-07 实测：一次排空共 45 条，首帧 `BD0805`、其余 44 条 `BD0806`，
结束帧是 `BD0806 FFFFFFFF FFFFFF 00`。旧文档写成「每条都是 BD0805」是错的。）
```

原小程序的处理：`00`（开始）和 `01`（结束）都记一条，但 `01` 只在时长不为 0 时才记；
读到 `FFFFFFFF` 后再把整批记录同步到服务器。

> 注意：因为是流式推送，**只发 `DB 01 05` 不回确认，就只会拿到第一条**。
> 回确认时用的是"开始时间戳"，不是接收顺序号。

#### 一次性读取：`DB 01 05` 不是"从头扫一遍"★

**日志是待同步队列，不是可反复读的环形缓冲。** 发 `DB 01 05` 取队列中尚未确认的记录，
`DB 06 06 01` 确认一条就消费一条，`FFFFFFFF` 表示队列已空。上游小程序每收一条就上传
`uploads_device_use_log`、历史页从服务器读（[miniprogram.zh-CN.md](miniprogram.zh-CN.md) §5.2），
设备本地只存未同步的部分 —— 这正是队列的设计意图。

**已确认过的记录不再返回**：三次连续读取首尾严格接续、零重叠（下表），11-07 断电重启后
也没重现；2026-11-08 用 6 个历史时间戳（含 `00000000` / `FFFFFFFF`）发确认帧试图回溯，
全部只回 `FFFFFFFF`（§8.5）。
⚠️ 物理上是「删除」还是「不可回退的已读标记」，BLE 层无法区分，**不下结论**；
以下只描述可观测行为。不确认，再发一次 `DB 01 05` 会**重发同一条**（未出队）。

实测（2026-11-07，三次连续连接，期间设备没有执行过任何消杀）：

| 会话 | 本轮最后确认的一条 | 下一次的首条 |
| --- | --- | --- |
| 第 1 轮 | `0x00023760`（66 h） | `0x00030570`（55 h）← 正好接上 |
| 第 2 轮 | `0x69CEAEA0`（2026-04-03 02:00） | `0x69CD5D20`（2026-04-02 02:00）← 正好接上 |

另一条佐证：发 `DB 01 05` 拿到 `0x00084B70` 但**不回确认**，再发一次 `DB 01 05`，
收到的**还是 `0x00084B70`**。

⟹ 实现上的三个后果：

1. **点一次「读取记录」拿到的是"尚未确认的接下来 N 条"，不是"最新 N 条"。**
   连点两次得到两段不重叠的记录，**读过的不会再回来**，看起来像"记录变少/丢了"。
   要留档就在第一次读取时把输出存成文本。
2. **不回确认就不出队**，重复发查询只会拿到同一条，容易误判成"卡死"。
3. **队列排空后无法用协议回溯**：ACK 结束标记、重新对时、读定时表、完整初始化序列，
   以及任意历史时间戳的确认帧，回包一律 `BD0805/BD0806 FFFFFFFF FFFFFF 00`。
   **下一次定时消杀写入新记录后，日志会重新可读**（11-08 07:09 实测，见 §8.5）：
   跨过 02:00 定时点后，裸发 `DB 01 05` 收到
   `BD0805 6AEF6720 00B4 00 00`（02:00 / 180 s / 定时 / **开始类**），ACK 后即结束标记。
   ⟹ **USB 常供电不需要长按重启**：等下一个定时点即可；重启也找不回已消费的记录。
   另：`DB 02 04 01` 命令触发的消杀**未见新增日志**（一次对照），定时触发的才写（§8.5）。

> **旧推断「断电真丢记录」已撤回（2026-11-08 复核）。** 当时看到 11-07 重启后
> B 类时间戳与 `2026-04-03` 消失、日志链从 `04-02` 开始，推测是"最近若干条未落盘"。
> 把三轮 dump 按时间摊开后可见，这些记录**都在此前各轮被确认消费过**：
> s1 `11-01 → 05-08`、s4 `05-08 → 04-03`、s6 `04-02 → 02-18`，首尾接续、零重叠。
> 用「已消费」解释更简洁，不需要额外假设掉电丢失。**断电是否额外丢记录，未证实。**

几个实测到的特性：

- **队列内顺序是最新的在前**；
- **45 不是缓冲容量**：三次读取分别拿到 37 / 42 / 45 条，只是各次**未读队列长度**。
  真实容量未知；§8.3 曾写「深度 ≥ 42」、§8.4 写「= 45」，都是把队列长度误当容量；
- 45 条里 44 条 `20..22` = `01`（结束），**最老一条是 `00`** —— 所以「恒为 01」不成立，
  「开始」类记录确实存在，只是极少。本轮 45 条时长全是 180 s（另在 §8.2 实测过 300 s）；
- 时间戳分两类。**A 类**：真实 unix 秒（本轮 44 条，`2026-02-18` ~ `2026-04-02`，
  每天 02:00，间隔精确 24 h）。**B 类**：接近 0 的小值（`00000000`、`0003D4C2`、
  `00030570` 等），**恰好都是 3600 的整数倍**，相邻间隔精确交替 **13 h / 11 h**
  （对应 `02:00` 与 `15:00` 两个定时）。
- B 类在后续读取中不再出现、A 类接着出现，与「按时间顺序消费」一致；之前
  「B 类只存 RAM、断电丢失」是**推断，已撤回**。B 类为何是 3600 的整数倍仍未查明
  （USB 常供电后不再产生，见 §9）。两类记录都**必须回确认**，否则后面的取不到。

## 6. 连接后的初始化时序

小程序原逻辑，可直接照搬：

```
连接
 → 订阅所有可 notify 的特征值（重点：1002）
 → DB 04 02 + 当前 unix 秒      // 对时 + 拉状态
 → DB 01 05                     // 拉消杀日志
 → DB 01 07                     // 拉定时列表（关键）
 → DB 01 A4                     // 版本
 → DB 04 02 + 当前 unix 秒      // 再同步一次
```

15 秒内若未收到完整状态回包，小程序会主动断开重连。

> **帧间隔别太短**（2026-11-08 实测）：间隔 0.25 s 连续读 12 轮，8 轮收不到
> `BD0D07`；拉到 0.6 s 后 8 轮全中。`set_timer.py` 用 1.2 s，是安全的。
> 自己写客户端时，序列里相邻帧至少留 **0.5 s**。

## 7. 最小可用实现

想只用最小代码完成"改时间"，只需三步：

```python
# 1. 连接 BLE 设备
#    广播名可能是 QUANGE-WY020702，也可能是模块默认名 kHID（GAP 名 Hi- 开头）
#    —— 三个前缀都要认，或者干脆按 MAC 连。别只写死 "QUANGE"。
#    另外：广播里带 0x1812，但它和名字出自同一块配置（设备实际没有 HID 服务），
#    改名后这个声明也可能一起消失 —— 别把它当稳定标识，MAC 才是。
# 2. 写 DB 08 08 <条数> <HH> <MM> <0D> 到 00001001-...（write-without-response）
# 3. 写 DB 04 02 + unix秒 到同一特征值，订阅 1002 听回包确认
```

**只改定时表不需要 `DB 01 05`** —— `DB 01 05` 是"查日志"，和写定时无关。

需要**回读**当前定时列表时，时序是三条依次发：

```
DB 04 02 + ts     对时（先对时，否则设备侧时间戳不可靠）
DB 01 05          查日志（可选；发日志前通常先对时）
DB 01 07          读定时列表 → 回 BD 0D 07
```

`DB 01 05` 是**流式推送**：设备一条一条给，每收到一条必须回
`DB 06 06 01 + 该条起始时间戳` 才会给下一条，直到收到 `FFFFFFFF` 为止。
**只发不确认就只能拿到第一条。**

注意 Windows 默认 MTU 为 23，单次写入上限 20 字节。本协议**最长 16 字节**
（4 条定时的写入帧 `DB 08 08 04` + 12 字节，以及 `BD 0D 07` 的 4 槽回读帧），
仍在 20 字节以内，**无需分片**；若将来扩展超过 20 字节，需自己切片。

## 8. 实测验证记录

### 8.1 2026-10-22（Windows + `bleak`，距离约 30 cm，RSSI −55 ~ −72 dBm，连接稳定）

| 步骤 | 发送 | 收到 | 结论 |
| --- | --- | --- | --- |
| 通道验证 | `DB 02 04 01` | `BD0B02 01 00B4 0000 64 0005 EEC0 00` | 指示灯转呼吸，设备执行 |
| 写入定时 | `DB 08 08 01 03 00 05` | `BD0D08 030005 FF×9 0C` | 保存成功，原列表被覆盖 |
| 状态确认 | `DB 04 02 + ts` | `BD0E02 00 ...` | 下次杀菌 = 2026-10-23 03:00:00 |
| **多条定时** | `DB 08 08 02 03 00 05 0F 1E 04` | `BD0D08 030005 0F1E04 FF×6 00` | 两条均被接受 |
| **回读列表** | `DB 04 02` → `DB 01 05` → `DB 01 07` | `BD0D07 030005 0F1E04 FF×6 00` | 读到同一组两条，完全一致 |
| 日志查询 | `DB 04 02` → `DB 01 05` | `BD0805 6AD9F79A 00B4 01 01` | 成功解析出「开始时间 / 180 秒 / 类型 1 / 结束」 |
| 日志流式确认 | `DB 06 06 01` + 起始时间戳 | 逐条返回 | **已验证**：连读 20 条，顺序最新在前，可继续往前追 |

### 8.2 2026-11-01（同一台设备，距离较远，RSSI −87 ~ −92 dBm，连接成功率约 1/3）

| 步骤 | 发送 | 收到 | 结论 |
| --- | --- | --- | --- |
| GATT 全量导出 | —（仅连接并遍历） | 6 个服务，**无 HID 服务** | `000000FB` 与 Telink OTA 均存在；`0x1812` 确认只是广播声明 |
| PnP ID | 读 `2A50` | `02 8A 24 66 82 01 00` | `VID=0x248A`（Telink）、**`PID=0x8266`**（小端）。⚠️ 该值是 SDK 默认常量，**不能据此判断芯片型号**，见 §1 |
| 电量 | 读 `2A19` | `63` | 99% |
| 固件版本 | `DB 01 A4` | `BD 06 A2 30 30 30 30 31 34` | 载荷是 **ASCII `"000014"`**，见下注 |
| **5 条定时** | `DB 08 08 05 02 00 06 08 00 03 0C 00 03 12 00 03 16 00 03` | `BD0D08 020006 080003 0C0003 120003 00` | **第 5 条被静默丢弃，固件上限 4 条** |
| **间隔 30 分钟** | `DB 08 08 02 02 00 06 02 1E 03` | `BD0D07 020006 021E03 FFFFFF FFFFFF 00` | **固件不校验间隔**，两条原样保存（见下注） |
| **时长生效** | 设定 `15:00 / 5min` 后等其执行 | 日志 `BD 08 05 6AE2EEF0 012C 00 01` | `0x012C` = **300 秒**，与 5 分钟一致（见下注） |
| 恢复并回读 | `DB 08 08 02 02 00 03 0F 00 05` → `DB 01 07` | `BD0D07 020003 0F0005 FFFFFF FFFFFF 00` | 与写入前逐字段一致 |

> **间隔限制只存在于小程序前端（实测）。**
> 上面第二行写入的两条定时相隔 **30 分钟**，远小于前端要求的 59 分钟，设备原样接受。
> 结合 `app-service.js` 的 `±59` 与 `1380` 判断，可以确定：
> **「≥59 分钟」和「23 小时窗口」都是纯前端规则，固件完全不校验。**
> `set_timer.py` / `phone.html` 仍保留这两条校验，是**有意与小程序保持一致**，
> 避免用户设出原厂 App 里做不到的配置；要绕过用 `--force`。

> **定时时长 `0D` 确实生效（实测）。** 日志记录 `BD 08 05 6A E2 EE F0 01 2C 00 01` 中，
> 时间戳 `0x6AE2EEF0` = 2026-10-29 15:00:00，时长 `0x012C` = 300 秒，
> 正好对应定时表里的 `15:00 / 5min`。**设备认可并执行 `0D` 字段的时长。**

> **日志 `type` 字段区分触发方式（实测）**：`type 0` 的时间戳都是整点
> （02:00:00 / 15:00:00）= **定时触发**；`type 1` 是 `19:09:09` 这类随意时刻 = **手动/按键触发**。

> **`BD 06 A2` 的载荷是 ASCII 字符串**：6 字节 `30 30 30 30 31 34` 就是 `"000014"`。
> 小程序取 hex `15..16` 与 `17..18` 拼数的做法，在这台设备上得到 `14`，
> 只是因为 ASCII 数字恰好落在那两个下标上 —— **算法本身不正确，只是碰巧对**。
> 正确读法是 `payload.decode("ascii")`。
> （OTA 全流程见 [miniprogram.zh-CN.md](miniprogram.zh-CN.md) §5.1。）

由此确认：写 `1001` 有效，回包走 `1002`，无需任何绑定。`1001` 的 CCCD 写入被拒
（`Write Not Permitted`），但数据写入不受影响，回包只从 `1002` 出。

> **写完不一定有回包。** 2026-11-01 恢复定时表那次没有收到 `BD 0D 08`，
> 但回读发现数据其实已经写进去了。**判断成败必须回读，不能靠回包。**

### 8.3 2026-11-07（同一台设备，RSSI −86 ~ −95 dBm，连接成功率不足一半）

| 步骤 | 发送 | 收到 | 结论 |
| --- | --- | --- | --- |
| 未订阅先发状态帧 | `DB 04 02` + ts（此时未订阅 `1002`） | **0 帧** | 回包被丢弃 |
| 之后补订阅 | 订阅 `1002`，等 6 s | **仍 0 帧** | **不缓存，不补发** |
| 已订阅后重发 | 同上 | `BD0E02 00 012C 0000 64 6AEF6720 6AEF3956` | 立刻回包；`next run` = `2026-11-08 02:00:00` |
| 空转监听 | —（连接后 12 s 不发任何帧） | **0 帧** | **待机期间**不主动推送（消杀期不测，见 §9） |
| 未 ACK 后重发查询 | `DB 01 05` ×2，中间不 ACK | 两次都收到 `BD0805 00084B70 012C 00 01` | 未确认不出队，重发同一条 |
| 连续读取 | `DB 06 06 01` ×42 | 42 条，止于 `0x69CEAEA0`（2026-04-03 02:00） | 当时**未读队列 ≥ 42 条**（非容量，见 §5.3） |
| **跨连接续读** | 断开重连后再发 `DB 01 05` | 首条 `0x69CD5D20`（2026-04-02 02:00） | **已消费的不重现**，队列接着走（见 §5.3） |

> **日志时间基异常（实测，机制未查明）。** 同一时刻：
> - 状态回包的 `next run` = `0x6AEF6720` = **2026-11-08 02:00:00**（正确的墙钟）
> - 日志 ts = `0x00030570` = 198 000 s（不是墙钟），且整批**全是 3600 的整数倍**：
>   `0 h / 7 h / 18 h / 31 h / 42 h / 55 h`，相邻间隔精确交替 **13 h / 11 h**
>   —— 正是 `02:00` 与 `15:00` 两个定时的间隔。
>
> 结论只到"日志与调度用两套时间基"，**为什么、以及如何换算回墙钟，未查明**。
> （本机改 USB 常供电后时钟不再丢失，B 类记录不再产生，此项已关闭，见 §9。）

### 8.4 2026-11-07 晚（电脑移到设备旁，RSSI −70 ~ −82 dBm，连接稳定）

设备由用户长按重新上电（**上电后会自动消杀一次**）。两次连接分别跑完只读项与写入项；
**所有写入用例结束后已恢复原定时表并回读确认**（见末行）。

| 步骤 | 发送 | 收到 | 结论 |
| --- | --- | --- | --- |
| 状态回包 | `DB 04 02` + ts（已订阅 `1002`） | `BD0E02 00 00B4 0000 64 6AEF6720 6AEF443F` | `next run` = 11-08 02:00；`6AEF443F` = 设备当前时钟 **23:31:11**，对时生效 |
| 日志排空 | `DB 01 05` → `DB 06 06 01` ×45 | 45 条 + `BD0806 FFFFFFFF FFFFFF 00` | **未读队列 45 条**（非容量，见 §5.3）；首帧 `BD0805`，其余 `BD0806` |
| 队列排空 | 排空后再发 `DB 01 05` | `BD0805 FFFFFFFF FFFFFF 00` | 已消费的记录**不再返回** |
| 空转监听 | —（10 s；另一轮 60 s） | 0 帧 | **待机期间**不主动推送（消杀期不测，见 §9） |
| **删除帧** | `DB 00 08 01 020003` | `BD0D08 020003 FF×6 00` | 删除帧生效（此前只有源码推断） |
| 删除帧清空 | `DB 00 08 00` | 本窗口 0 帧；下一窗口收到全 `FF` 空表 | 清空生效，回包延迟 |
| **时长边界** | 时长字节 `00` / `0F` / `07` | 回包分别 `020000` / `02000F` / `020007` | **固件不校验时长**；3~6 分钟是纯前端规则 |
| 间隔复核 | 30 min / 59 min 各一组 | 两组均原样保存 | 与 §8.2 一致 |
| 1~4 条 | `DB 08 08 01..04` | 槽位数与条数一致，末字节恒 `00` | 4 槽结构复核 |
| **恢复并回读** | `DB 08 08 02 020003 0F0005` → 全序列 `DB 01 07` | `BD0D07 020003 0F0005 FF×6 44` | 与测试前逐字段一致 |

> **写入回包会延迟到下一个命令窗口。** 12 个用例里 4 个当场 0 回包，但它们的
> `BD0D08` 都出现在紧接着的下一个用例窗口里（`del0` 的空表落在 `dur00`，`dur0F` 的
> `02000F` 落在 `dur07`）。这印证 §8.2「写完不一定有回包」并给出机制：**不是丢失，
> 是延迟**。客户端仍必须回读，不能靠回包判成败。

> **开机自动消杀留下一条日志。** 排空得到的第 1 条是 `BD0805 00000000 00B4 01 01`
> （`ts=0` / 180 s / `type=1` / 结束），与用户「长按打开后会自动开始消杀」吻合；
> 重启后时钟未对时，所以 ts 为 0。**仅一次观察**。

> **断电前后日志链变化（2026-11-08 重新解释）。** 断电前（§8.3）读到一批 B 类
> 「3600 整数倍」时间戳和 `2026-04-03`；上电后排空的 44 条历史记录全是 A 类真实 unix 秒
> （`2026-02-18` ~ `2026-04-02`）。当时记为「断电丢记录」，现按 §5.3 的消费式队列解释：
> **这些都是前几轮已确认消费过的**，链自然接到 `04-02`。断电是否额外丢记录，未证实。

### 8.5 2026-11-08（USB 常供电，RSSI −70 ~ −74 dBm，连接稳定）

> 实测机已由用户改为 **USB 常供电**：不再自动关机、不再掉时钟，因此
> 「断电 / 换电池」相关现象在本机不再复现，§9 中相应条目已主动关闭。

| 步骤 | 操作 | 结果 | 结论 |
| --- | --- | --- | --- |
| 末字节采样 | 12 轮全序列读表（间隔 0.25 s） | 仅 4 轮收到 `BD0D07` | **帧间隔太短会丢回包** |
| 末字节受控 | 对时帧时间戳第 3 字节依次设 `4D` / `4E` / `4F` | 末字节精确跟随 `4D` / `4E` / `4F`，重复发回 `00` | **时钟派生字段，忽略即可** |
| 间隔修正 | 同样序列改为 0.6 s | 8/8 轮收到 | 相邻帧至少留 0.5 s |
| 假时钟 | `DB 04 02` + `0x00000100` | 状态回包回显 `00000100`，`next run` = `0x6270` | **时间戳即设备时钟；按 UTC+8 本地 HH:MM 判定时** |
| 消杀中状态 | 假时钟下 `DB 02 04 01`，每 30 s 采样 ×6 | 6/6 回 `BD0E02 01`，`12..16` 30→160 s 递增后归零 | **计数器 = 总量 / 已过；消杀期间回包正常** |
| 队列回溯尝试 | ACK `FFFFFFFF` / 重新对时 / 读表 / 完整序列 | 全部仍返回 `FFFFFFFF` | 已消费记录**不可再访问** |
| 历史时间戳回溯 | `DB 06 06 01` + 6 个历史 ts（02-18 / 04-02 / 11-01 / 11-08 / `00000000` / `FFFFFFFF`） | 6/6 只回 `BD0806 FFFFFFFF`，随后 `DB 01 05` 也 `FFFFFFFF` | **无法按时间戳定位或重放历史** |
| 真时钟消杀（命令触发） | `DB 02 04 01` 跑满 209 s 后再读日志 | 仍 `BD0805 FFFFFFFF` | **命令触发的消杀不写日志**，不能据此判断队列行为 |
| 定时点复测 | 07:09 跨过 02:00 定时点后裸发 `DB 01 05` | `BD0805 6AEF6720 00B4 00 00`，ACK 后 `BD0806 FFFFFFFF` | **定时消杀写入新记录，日志自动重新可读** |
| 广播名 | 扫描 60 s → 连接 → 再扫描 60 s | 每轮仅第 1 个包是 `kHID`（1/121、1/98），其余全是 `QUANGE-WY020702` | **不是轮换；启动瞬间的默认名 + 随即固定** |

> **一次性读取与 USB 常供电**：日志是待同步队列（§5.3），ACK 一条消费一条，排空后
> 协议手段无法回溯，但**不需要上电** —— 下一个定时点写入新记录后即可再读。02:00 定时
> 执行也由状态回包印证：`BD0E02 00 00B4 0000 64 6AF01DF0 6AEFAFB5`，`next run` 已推进到
> 11-08 15:00，设备时钟 07:09:41、电量 100%、待机。
> ⚠️ 旧的「读取游标 + 环形缓冲 45 条」模型已被推翻：三轮 dump 首尾接续零重叠（跨断电
> 重启也不重现）、6 个历史时间戳回溯全部失败，45 只是当时未读队列长度。物理上是删除
> 还是已读标记无法区分。另：`DB 02 04 01` 命令触发的消杀不写日志，上一轮据此误判过。
> 定时表读写全程不受影响；设备时钟均为真实 unix 秒，定时表保持
> `02:00/3min + 15:00/5min`。

## 9. 未验证 / 存疑

> 已在真机确认的条目见 §8.2 – §8.5。以下只保留**仍未解决**、且值得继续投入的问题。

- **Telink 具体型号** —— BLE 层已穷举无解：180A 只有 `2A50`，PID `0x8266` 是
  Telink SDK 写死的默认值；本机也没有 `2A27` Hardware Revision。用户只是把电池换成
  USB 供电线，**外壳拆不开**，丝印路径同样不可用。
  ⚠️ 这卡死 `TLSR825x_OTA_Flash_Hacker`（[live-test](live-test-2026-10-29.md) §7）：
  `BLE-Hacker.bin` 只编译给 TLSR8258，本机型号无法确认且无原厂固件可回滚。
  2026-11-08 源码核对：TelinkMiFlasher 的 UUID / `01ff` 握手 / `02ff`+count+`~count`
  结束帧与本机小程序**完全同源**（仅数据块 32B vs 16B），工具很可能真能写入
  —— 风险是真实的，不是「刷不进去所以安全」。
- **多个定时点后日志是否都稳定可读** —— 已确认一次（11-08 02:00，见 §8.5），
  USB 常供电不需要长按重启。尚缺**第二次及连续多天**的重复验证；下一次自然定时点
  是 11-08 15:00，到点再读一次即可，无需专门实验或改动设备状态。
- **日志队列的物理机制与容量** —— 行为已实测（ACK 即消费、无法回溯），但
  「物理删除」与「不可回退的已读标记」在 BLE 层不可区分；真实容量也未知
  （37 / 42 / 45 都只是各次未读长度）。除非拆机读 Flash，否则不追。

**已主动关闭，不再追踪**（附理由，避免以后重复投入）：

| 条目 | 关闭理由 |
