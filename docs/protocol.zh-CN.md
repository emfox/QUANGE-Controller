# 全格 WY020702 蓝牙协议全文

> 本文档由逆向已下线的微信小程序「莱枫智能生活」（appid `wx9528fce803d3ba0e`，v18）得出。
> 所有条目均经过真机实测验证，验证过程见第 8 节。

---

## 1. 传输层

| 项 | 值 |
| --- | --- |
| 广播名 | `QUANGE-WY020702` **或** `kHID` —— 实测会在两者之间切换 |
| GAP 设备名 | `Hi-YM01-XXXXXXXXXXXX` |
| 广播内容 | Service UUID `0x1812`(HID) + `0x180F`(Battery)，Manufacturer Data 前三字节等于 MAC 前缀 |
| 芯片 | Telink（泰凌微），PnP ID `0x248A:0x6682` |
| 配对要求 | **无**。不需要配对、绑定、加密 |
| 帧加密 | **无**。明文十六进制 |
| 校验 | **无**。无 CRC、无校验位（OTA 除外） |

> **别混淆两件事**：这里说的"无加密"指的是**设备之间的 BLE 帧**。
> 小程序包本身是**有加密**的（`V1MMWX` 容器，去掉 6 字节头后整段 XOR 0x30），
> 那是发布方的包壳保护，跟设备协议没有关系。
> 换句话说：**包要解密，协议不用。**

> 广播里不含私有服务 UUID，因此扫描时无法按服务过滤，只能按名称过滤或显示全部设备。

### GATT 结构

| Service | Characteristic | 属性 | 用途 |
| --- | --- | --- | --- |
| `00001800` | `2A00` / `2A01` / `2A04` | read | 标准 GAP |
| `00001801` | `2A05` | indicate | 标准 GATT |
| `0000180A` | `2A50` | read | PnP ID |
| `0000180F` | `2A19` | read / notify | 电量 |
| `000000FB` | **`00001001-0000-1000-8000-00805F9B34FB`** | read / **write-without-response** / notify | **指令下发** |
| `000000FB` | **`00001002-0000-1000-8000-00805F9B34FB`** | read / notify | **设备回包** |
| `00010203-0405-0607-0809-0A0B0C0D1912` | `...0A0B0C0D2B12` | read / write-without-response | OTA 升级专用 |

`1001` 的 CCCD 受权限保护（订阅会返回 `Write Not Permitted`），但**写入不受限制**；
回包走 `1002`，可以正常订阅。

## 2. 帧总则

- 方向：主机 → 设备，帧首字节 `0xDB`；设备 → 主机，帧首字节 `0xBD`
- 字节序：多字节字段一律**大端**
- 数值字段一律以**数值本身**表示（不做 BCD 转换）：15 点 = `0x0F`，不是 `0x15`

### 帧结构

```
DB | CMD | SUB | [LEN] | [DATA...]
```

`CMD` + `SUB` 组成功能码，例如 `DB 02 04` 是开关类，`DB 08 08` 是设定时类。

## 3. 指令表

| 功能 | 帧 | 回包 |
| --- | --- | --- |
| 立即开启（消杀） | `DB 02 04 01` | `BD 0B 02` |
| 关闭 | `DB 02 04 00` | `BD 0B 02` |
| 查询状态 | `DB 04 02` + 4B unix 秒 | `BD 0E 02` / `BD 11 02` / `BD 00 02` / `BD 02 02` |
| **查询定时列表** | **`DB 01 07`** | `BD 0D 07` |
| 查询消杀日志 | `DB 01 05` | `BD 08 05` |
| 设置定时（整表覆盖） | `DB 08 08` + `Count` + `[HH MM 0D] × Count` | `BD 0D 08` |
| 删除定时 | `DB 00 08` + `Count` + `[HH MM 0D] × Count` | — |
| 版本 | `DB 01 A4` | `BD 06 A2` + ASCII 版本串（实测 `000014`） |
| 设备复位 | `DB 01 A0` | — |
| 日志确认 | `DB 06 06 01` + 4B 时间戳 | — |
| OTA 分包 | `01 FF` / `02 FF ...` | — |

> `DB 01 07` 单独发送时设备**不回复**。必须先走一遍完整时序
> `DB 04 02` → `DB 01 05` → `DB 01 07`，才会收到 `BD 0D 07`。
> 这是本协议最反直觉的一点，实测踩过坑。

### 3.1 开关

```
DB 02 04 01     开启（UVC 工作约 3 分钟，指示灯呼吸）
DB 02 04 00     关闭
```

### 3.2 查询状态

```
DB 04 02 | TS(4B 大端, unix 秒)
```

时间戳一方面让设备校准时钟，一方面触发状态回包。**每次连接后建议先发这一帧。**

### 3.3 设置定时

```
DB 08 08 | Count(1B) | [HH(1B) MM(1B) 0D(1B)] × Count
```

- `Count`：本次写入后的**总条数**，设备按整表覆盖处理
- `HH`：小时，0–23
- `MM`：分钟，0–59
- `0D`：消杀时长，只支持 **3 / 4 / 5 / 6** 分钟（`0` 是固定前缀）

示例：

| 需求 | 帧 |
| --- | --- |
| 每天 03:00，5 分钟 | `DB 08 08 01 03 00 05` |
| 每天 02:00，3 分钟 | `DB 08 08 01 02 00 03` |
| 03:00/5min + 15:30/4min | `DB 08 08 02 03 00 05 0F 1E 04` |

**多条定时已实测可用**：写入两条后，设备回 `BD0D08 030005 0F1E04 FF FF FF FF FF FF 00`，
`DB 01 07` 回读得到同样的两条。

**关于「4 条」这个上限**：它出自小程序 `problem` 页的 FAQ 文案
（"…最多设置四条消杀,最少一条。"），**代码里并没有硬编码这个数字** ——
所以它是原厂的产品约定，不一定是固件限制。按 4 条设计最稳，但想试第 5 条也没有代码会拦你。

**空槽与尾字节**：`BD0D07` / `BD0D08` 的载荷是定长槽位（每槽 3 字节，空槽 `FF FF FF`），
末尾还有一个 1 字节字段（实测出现过 `0C`、`00`，含义未明，写入时不需要它）。
解析时跳过 `FF` 槽、忽略末字节即可。

> 因为语义是整表覆盖，**不需要先读出当前列表**，直接写目标列表即可。

### 3.4 删除定时

```
DB 00 08 | 剩余条数(1B) | [要保留的项] × 剩余条数
```

小程序源码里的拼接是 `"DB00080" + 剩余条数 + 保留项`。注意 `"DB00080"` 是 **7 个字符**，
末尾的 `0` 会和条数拼成同一个字节，所以落到线路上就是：

| 剩余条数 | 实际帧 | 说明 |
| --- | --- | --- |
| 1 | `DB 00 08 01 03 00 05` | 第四字节 = `01` |
| 2 | `DB 00 08 02 03 00 05 0F 1E 04` | 第四字节 = `02` |
| 0 | `DB 00 08 00` | 清空整个定时表 |

**第四字节是剩余条数**（与新增/修改帧的 `DB 08 08 | 总条数` 语义一致），
只带**要保留**的项，不要带要删的项。

> 源码里这个数字叫 `listLen`，值来自 `t.len - 1`（编辑页传入的现有总条数减 1），
> 删掉一项后正好等于「剩余条数」。
> 因为上限只有 4 条，`0N` 看起来像 BCD，但它是普通十六进制整数，直接按数值写即可。

## 4. 定时项编码细节

设备内部把定时表存成定长槽位，每槽 3 字节。回包中空槽以 `FF FF FF` 填充。

例：只设一条 03:00/5min 时，`BD0D08` 回包为

```
BD 0D 08 | 03 00 05 | FF FF FF FF FF FF FF FF FF | 0C
                        └── 3 个空槽（共 9 字节）
```

已实测 **2 条**同时写入并回读一致；上限按小程序 FAQ 里写的 **4 条**设计
（该数字只出现在文案里，代码未硬编码，见 §3.3），固件是否接受更多未验证。

## 5. 回包解析

回包一律 `BD` 开头。**命令字并不固定**，实测出现过 `BD0B02` / `BD0D08` / `BD0E02` 等多种。

判定方式：**取前 6 个 hex 字符（3 字节）作为命令字，精确匹配**。
小程序源码就是这么做的 —— `buf2hex(value).substring(0,6)` 然后一串 `else if("bd0b02"==a)`。
`phone.html` 和 `set_timer.py` 也用同一套规则。

```
前缀（hex 0..6）        含义
BD 0B 02 / BD 0E 02 /
BD 11 02 / BD 00 02 /
BD 02 02                状态类（见 5.1）
BD 0D 07                定时列表回读（见 5.2）
BD 0D 08                定时保存成功（见 5.2）
BD 08 05 / BD 08 06     消杀日志（见 5.3）
BD 06 A2                固件版本
BD 05 A1                低电量告警
```

> 别用「第 4 字节是不是 `0x00/0x01`」来判类型 —— `BD0B02` 的第 4 字节是 `0x00`、
> `BD0D07` 是 `0x07`，这个规则会把 `BD0B02` 当成状态、`BD0E02` 当成别的。
> 老老实实枚举命令字即可。

### 5.1 状态类（`BD0B02` / `BD0E02` / `BD1102` / `BD0002` / `BD0202`）

下标均指**十六进制字符串**的下标（1 hex char = 4 bit，2 个 hex = 1 字节）。
五个命令字共用同一套字段布局。

| hex 下标 | 长度 | 含义 |
| --- | --- | --- |
| `0..6` | 6 | 命令字 |
| `6..8` | 2 | 状态：`01` 正在消杀 / `00` 待机 |
| `8..12` | 4 | 消杀开始时间戳（低 32 位片段） |
| `12..16` | 4 | 当前时间戳片段 |
| `16..18` | 2 | 电量百分比（hex，`64` = 100%） |
| `18..26` | 8 | **下次杀菌 unix 时间戳**（仅待机时有） |

待机时剩余秒数不需要算；消杀中可用 `sub(8,12) - sub(12,16)` 得到剩余秒数。

> **为什么不能无脑读 `18..26`：**
>
> 只有**待机**回包（状态 `00`）才有 `18..26` 这段下次杀菌时间戳。
> 状态为 `01`（消杀中）时，实际回包缺这段，硬读 `sub(18,26)` 会拿到
> `0005EEC0` 之类的值，换算出来是 1970 年。
>
> 正确做法：**先看 `6..8` 状态字节，再决定要不要读 `18..26`**；
> 或者读完做一次合理性校验（`> 1600000000`，即 2020-09 之后）。
> `phone.html` 和 `set_timer.py` 都是这么做的。
>
> 注意：本节两个样本是从早期记录里转抄的，转抄时字节分组做过简化，
> **不能当成完整帧长度来用**。判断字段位置请以下标表为准，不要去数样本的字节数。

实测样本（立即开启，状态 `01`）：

```
BD 0B 02 | 01 | 00 B4 | 00 00 | 64 | 00 05 | EE C0 | 00
           ↑消杀  ↑180s   ↑已过0  ↑100%  ↑时长
```

实测样本（待机，已设定 03:00）：

```
BD 0E 02 | 00 | 00 B4 | 00 00 | 64 | 6A DA 5D 30 | 6A D9 F8 82
           ↑待机              ↑100%   ↑下次杀菌     ↑当前时间
                                        = 2026-10-23 03:00:00
```

### 5.2 定时列表（`BD0D07` / `BD0D08`）

`BD0D07` 是查询结果，`BD0D08` 是保存成功。载荷为定长槽位表，每槽 3 字节，空槽 `FF FF FF`。

### 5.3 日志（`BD0805` / `BD0806`）

| hex 下标 | 含义 |
| --- | --- |
| `6..14` | 开始时间戳（8 hex，unix 秒） |
| `14..18` | 持续时长（秒） |
| `18..20` | 动作类型 |
| `20..22` | `00` 开始 / `01` 结束 |

实测样本：

```
BD 08 05 6A D9 F7 9A 00 B4 01 01
         ↑开始时间戳  ↑180s  ↑类型1 ↑结束
```

**这是一条"流"：设备逐条推送，必须回一次确认才会给下一条。**

流程：

```
发 DB 01 05
  → 收 BD0805（第 1 条）
  → 回 DB 06 06 01 + 该条的开始时间戳（4 字节）
  → 收 BD0805（第 2 条）
  → 回 DB 06 06 01 + 时间戳
  → ……
  → 收到 sub(6,14) == FFFFFFFF 且状态为 00 时，表示没有更多记录
```

原小程序的处理：`00`（开始）和 `01`（结束）都记一条，但 `01` 只在时长不为 0 时才记；
读到 `FFFFFFFF` 后再把整批记录同步到服务器。

> 注意：因为是流式推送，**只发 `DB 01 05` 不回确认，就只会拿到第一条**。
> 回确认时用的是"开始时间戳"，不是接收顺序号。

**实测（2026-10-22，真机）**：确认机制工作正常 —— 连续读到 20 条，每回一次确认才收到下一条。

几个实测到的特性：

- **顺序是最新的在前**；
- 设备内部是**环形缓冲**，深度未知：读满 20 条仍未结束，继续读还能往更早追；
- 每条记录都是**已完成**的一次消杀，状态位恒为 `01`，时长实测都是 180 秒；
- 部分历史记录的时间戳接近 0（见过 `00000000`、`0003D4C2` 这类），
  说明**设备时钟被重置过**（换电池后未对时）。这类记录的时间应视为"未知"，
  但**仍必须回确认**，否则后面的记录取不到。

### 5.4 告警

`BD05A1` = 电量过低。

## 6. 连接后的初始化时序

小程序原逻辑，可直接照搬：

```
连接
 → 订阅所有可 notify 的特征值（重点：1002）
 → DB 04 02 + 当前 unix 秒      // 对时 + 拉状态
 → DB 01 05                     // 拉消杀日志
 → DB 01 07                     // 拉定时列表（关键）
 → DB 01 A4                     // 版本
 → DB 04 02 + 当前 unix 秒      // 再同步一次
```

15 秒内若未收到完整状态回包，小程序会主动断开重连。

## 7. 最小可用实现

想只用最小代码完成"改时间"，只需三步：

```python
# 1. 连接 BLE 设备
#    广播名可能是 QUANGE-WY020702，也可能切到 kHID（还有 Hi- 开头）
#    —— 三个前缀都要认，或者干脆按 MAC 连。别只写死 "QUANGE"。
# 2. 写 DB 08 08 <条数> <HH> <MM> <0D> 到 00001001-...（write-without-response）
# 3. 写 DB 04 02 + unix秒 到同一特征值，订阅 1002 听回包确认
```

**只改定时表不需要 `DB 01 05`** —— `DB 01 05` 是"查日志"，和写定时无关。

需要**回读**当前定时列表时，时序是三条依次发：

```
DB 04 02 + ts     对时（先对时，否则设备侧时间戳不可靠）
DB 01 05          查日志（可选；发日志前通常先对时）
DB 01 07          读定时列表 → 回 BD 0D 07
```

`DB 01 05` 是**流式推送**：设备一条一条给，每收到一条必须回
`DB 06 06 01 + 该条起始时间戳` 才会给下一条，直到收到 `FFFFFFFF` 为止。
**只发不确认就只能拿到第一条。**

注意 Windows 默认 MTU 为 23，单次写入上限 20 字节，本协议最长为 10 字节，无需分片；
但若将来扩展，需按 20 字节切片。

## 8. 实测验证记录

环境：Windows + Python `bleak`；距离约 30 cm，RSSI −55 ~ −72 dBm。

| 步骤 | 发送 | 收到 | 结论 |
| --- | --- | --- | --- |
| 通道验证 | `DB 02 04 01` | `BD0B02 01 00B4 0000 64 0005 EEC0 00` | 指示灯转呼吸，设备执行 |
| 写入定时 | `DB 08 08 01 03 00 05` | `BD0D08 030005 FF×9 0C` | 保存成功，原列表被覆盖 |
| 状态确认 | `DB 04 02 + ts` | `BD0E02 00 ...` | 下次杀菌 = 2026-10-23 03:00:00 |
| **多条定时** | `DB 08 08 02 03 00 05 0F 1E 04` | `BD0D08 030005 0F1E04 FF×6 00` | 两条均被接受 |
| **回读列表** | `DB 04 02` → `DB 01 05` → `DB 01 07` | `BD0D07 030005 0F1E04 FF×6 00` | 读到同一组两条，完全一致 |
| 固件版本 | `DB 01 A4` | `BD06A2` + `"000014"` | 固件版本 `000014` |
| 日志查询 | `DB 04 02` → `DB 01 05` | `BD0805 6AD9F79A 00B4 01 01` | 成功解析出「开始时间 / 180 秒 / 类型 1 / 结束」 |
| 日志流式确认 | `DB 06 06 01` + 起始时间戳 | 逐条返回 | **已验证**：连读 20 条，顺序最新在前，可继续往前追 |

由此确认：写 `1001` 有效，回包走 `1002`，无需任何绑定。

## 9. 未验证 / 存疑

- 两条定时「间隔大于 1 小时」是前端校验还是固件也校验。
  **前端逻辑已核清楚**（`app-service.js` @addtime）：比较用的是 `±59` 而不是 `±60`，
  实际放行条件是**间隔 ≥ 59 分钟**（不是严格大于 60）；此外还有一条
  `r - a[0].min <= 1380`（23 小时）的附加限制，即所有定时都要落在首个定时的 23 小时内。
  这些**全是小程序前端校验**，固件是否也拦，未测。
- **定时时长（`0D`）是否真的生效** —— 日志里所有历史记录都是 180 秒，
  而我们设的是 5 分钟。等设定的时间点跑过一次后再读日志即可确认。
  （注：`0D` 里的 `0` 是小程序硬编码的前缀，见 §3.3，这部分已确认；待确认的是设备是否认这个时长。）
- 换电池后定时是否保留（推断保留）
- 日志环形缓冲的深度上限
- 是否存在「开始」类日志记录（实测全是 `01` = 结束）
- `BD 0D 07` / `BD 0D 08` 末尾那 1 字节的含义（实测出现过 `0C`、`00`）
- 定时时长字段 `0D` 的 `0` 是否真的是固定前缀，还是长度/类型标识
- `BD0D07` 完整字段布局
- 设备最多支持的定时条数
